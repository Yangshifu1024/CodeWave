## 共同设计约束

1. **事实源唯一**：持久化配置、项目注册表、任务表和指定会话草稿各有明确 owner。不得用旧 UI 快照、目录猜测或事件覆盖真值。
2. **提交后才宣称成功**：写入失败须保留原始数据或明确返回已提交部分。安全关键步骤失败禁止继续覆盖；结构化回执区分持久化成功、运行态应用、清理警告和需重试项。
3. **异步结果有身份**：至少绑定资源 ID 与修订号/世代；拿锁后复核，迟到结果不能覆盖新值、恢复已删除任务或重建已关闭 Tab。
4. **取消有确定边界**：锁内状态转换是领取/撤销的仲裁点；动作已开始时如不能中止须明确反馈，不能把“已暂停未来触发”显示成“当前运行已取消”。
5. **保持层次与接口契约**：`core/` 不引入 Tauri；IPC 做校验与转调；新持久字段按现行要求设置 serde 默认值，枚举默认值须体现未验证/未完成而非假成功；更新 `ipc/types.ts` 和调用方。不得把增量兼容等同于旧版可安全回滚。
6. **保持保真与权限**：Office 继续只替换目标 ZIP 内文件；路径规范化、写锁、审批与写入后检查不能因新 helper 漏接；MCP 调用失败后仍禁止自动重放非幂等操作；计划任务仍全局串行，权限不在本方案调整。
7. **可观测但不泄密**：记录资源 ID、阶段、错误类型与 revision，不记录密钥、base64 图片、完整 MCP 环境变量或用户文档正文。对外错误须脱敏；故障注入使用专用临时目录和假凭据。
8. **测试走真实接线**：纯 helper 单测之外覆盖 command → core → 磁盘/store → 展示的链路。竞争测试用 barrier/deferred promise/虚拟时钟控制顺序，不依赖任意 sleep 或历史“全绿”。

## R01 凭据提交不得先落明文或把降级伪装成功

### 场景与证据

用户首次添加供应商、替换密钥或保存含尚未迁移密钥的配置时，当前流程会先将密钥写入 `config.json`。即使钥匙串最终成功，临时文件、备份程序或同步软件也可能捕获该明文窗口；钥匙串拒绝访问、锁定或 Linux 无 Secret Service 时，明文会继续保留，而设置页仍可能显示“已保存”。损害是凭据泄露风险与用户对保存结果的误判；并非已有证据证明某台用户机器已经泄露。

**静态事实（基线 `8df75db5e9aeb6e9830892fba0e54ddd63856a9b`）：**

- [`save_config`](../src-tauri/src/host/commands/project.rs#L49-L89) 在第 70 行 `updated.save()` 后才调用 `keyring::migrate`；迁移警告只记日志，第 76–78 行只有迁移发生变化时才再写占位符。迁移失败但其它步骤成功时返回 `Ok`。
- [`migrate`](../src-tauri/src/host/keyring.rs#L30-L60) 写失败保留原明文；[`ConfigState::save`](../src-tauri/src/core/config.rs#L533-L539) 直接序列化完整配置。公共 [`atomic_write`](../src-tauri/src/util/atomic.rs#L7-L36) 会先写同目录临时文件，Windows 还可能复制已有文件为 `.bak`；原子替换不等于内容没有明文，也不等于钥匙串与配置构成一个事务。
- [`lib.rs` 启动入口](../src-tauri/src/lib.rs#L97-L107) 同样调用 `migrate`，且占位符配置回写失败被 `let _ = cfg.save()` 忽略。只改 IPC 保存会留下另一条入口。
- [`useSettings.save`](../ui/src/stores/settings.ts#L61-L66) 保存后把调用方 `next` 放回 store，没有读回后端归一化/脱敏结果；[`SettingsPage.save`](../ui/src/features/panels/SettingsPage.tsx#L862-L888) 在 IPC 成功后显示成功提示。

**反证与验证状态：** `get_config` 确实调用 [`sanitized`](../src-tauri/src/host/commands/project.rs#L38-L42)，掩码恢复也有匹配保护（[`unmask_from`](../src-tauri/src/core/config.rs#L605-L632)），但二者保护 IPC 展示，不改变先落明文的顺序。现有 [`migrate_and_resolve_roundtrip`](../src-tauri/src/host/keyring.rs#L155-L181) 接受钥匙串不可用时保留明文，不能作为新安全目标的验收。以上为源码核验；本次未调用真实钥匙串、未启动应用、未做故障注入或 GUI 点验，也未把已有测试描述为本次通过。

### 目标与设计

**目标：** 新提交的 API Key 不进入配置、临时配置、备份、提交记录或日志；凭据提交失败就不显示完整保存成功；配置文件持久化失败时，先前已提交配置仍解析到先前的密钥池；成功后的磁盘、运行态与 UI 权威快照一致。范围限供应商 API Key，不顺带把自定义请求头和代理密码迁入钥匙串，不保证抹掉历史备份、系统交换区或用户自行复制出的秘密。

**推荐：不可变版本化凭据账户 + 单一配置提交点。** 不采用“把 `migrate` 移到 `save()` 前面”作为完整修复：若仍原位覆盖 `provider.id` 对应账户，后续文件写失败时，旧配置里的占位符已经会读到新池；多供应商部分写成功也同样有半提交风险。

拟新增不依赖 Tauri 的配置提交协调器（如 `core/config_commit.rs`），通过 `CredentialStore` 与 `ConfigFileStore` 可注入接口执行，`host/keyring.rs` 提供系统适配，IPC 只校验/转调。`AgentCore` 持有进程内提交互斥锁；锁序固定为提交锁 → 短期 `cfg` 读/写锁，不持 `cfg` 锁调用系统钥匙串、磁盘或网络。阻塞操作在阻塞工作线程执行。所有写同一配置文件的入口均入协调器，至少包括 `save_config`、`set_font_prefs`、`toggle_skill`、命令审批“始终允许”的白名单追加及启动凭据整理；仅加 UI 按钮禁用不构成串行化。白名单旁路见 [`tools/command/tool.rs`](../src-tauri/src/tools/command/tool.rs#L774-L784)：当前先改内存后 `snapshot.save()`，既可能覆盖新配置，也绕过安全凭据整理。必须改为协调器中的去重字段 patch，禁止继续保存捕获的完整快照；持久化失败仍不阻塞本次已获批准的命令，但不得把“以后始终允许已保存”报告为成功，内存持久偏好也不能先行扩大。

提交协议如下：

1. 锁内读取最新配置及版本，做所有普通字段校验、字段所有权合并与冲突检查；密钥编辑先按 [R02](#r02-追加密钥必须保留已存池) 解析为明确意图。失败尚无外部写入。
2. 持久化模型新增 `ProviderConfig.credential_ref: Option<String>`（名称为建议，serde default 为 `None`）。`None` 仅在当前 v2 配置使用占位符时继续表示既有 `provider.id` 账户；新值由后端生成，账户命名绑定供应商 UUID 与随机 generation，如 `<provider>:credential:<generation>`。输入 DTO 不接受客户端自选账户；`flatten`、模型解析、标题/压缩、额度解析共用同一个引用决议器。空 keys 的供应商永不回读任何账户。
3. 对每个实际变更的池创建新账户，完整写入、读回校验。绝不覆盖旧账户。多供应商任一失败则取消整份配置提交，已创建的新账户作安全回收，不修改旧配置/旧内存。错误不含密钥或原始钥匙串 payload。
4. 新配置只含占位符和新引用。写前由可持久化 DTO 的断言/校验拒绝任何真实 API Key；使用已验证的文件替换路径完成一次配置提交。若文件失败，旧引用仍有效，新账户最多成为孤儿；不能通过恢复旧明文文件“补偿”新提交。
5. 文件提交成功为提交点，发布相同配置与递增版本到内存，再执行适用的日志/客户端/KeyPool 后处理。返回 `ConfigSaveResult { config: sanitized_snapshot, version, cleanup, warnings }`，保留原清理结果语义。凭据提交前失败是结构化错误；提交后的独立清理或垃圾回收失败是“配置已保存，后处理待重试”，不得伪装为未提交并诱导重复提交。store 只接受返回的权威脱敏快照，不再 `set({ config: next })`。
6. 旧账户延迟回收，不能刚提交就删：运行中的模型快照仍可能引用它。首版可保守推迟至下一次启动、且新配置完整可读后，再清理确认为应用创建且没有当前/保留恢复引用的账户。删除供应商/清空池在新提交配置中立即解除引用，新一轮从该配置决议的请求不回读旧池；物理删除失败单独可见，不能借 GC 状态把引用补回。已持有旧 `ModelConfig` 的请求/轮次仍按既有边界结束，不承诺即时撤销。源码 [`drive.rs`](../src-tauri/src/core/agent/drive.rs#L1516-L1535) 每次 retry 仍从传入的 `model` 解析 key，这正是旧版本账户必须延迟回收的原因；不能把“清空已保存配置”描述为立即使在途重试失效。

**崩溃可恢复性：** 系统钥匙串未必支持枚举应用账户，因此在写新账户前原子记录不含秘密的待清理意向（操作 id、应用生成的账户引用、所属 provider、阶段）。它只用于孤儿清理，不承担凭据真值。重启以成功读到的 `config.json` 引用为准：提交点前的候选账户可回收；已被引用者保留。配置损坏、无法确认引用或未来格式不认识时不做破坏性 GC。清理队列需去重、有界记录/压缩并可重试；队列写失败时中止创建新账户，避免无法登记的无限孤儿。断电耐久性另验目录同步及各平台替换语义，不能从现有 `atomic_write` 名称直接承诺断电原子性。

**没有可用钥匙串时：** 推荐拒绝新增/改变密钥的持久化，提示具体类别和重试路径，原有配置继续有效。不默认降级到明文、不弹“已保存”后仅在日志记录失败。会话级内存凭据可另行产品决策，不是本修复必需功能，也不能以此悄悄改成新的持久化模式。

替代方案是全量凭据改为独立加密文件，但需要主密钥管理、恢复和跨平台加密设计，范围更大；原位 keyring 写入后补偿恢复旧值成本较低，但恢复也能失败，且无法封住崩溃窗口，不能满足本项目的安全目标。

### 兼容与边界

- 这是当前 schema v2 数据的安全存储演进，不恢复已删除的 schema v1、旧品牌目录或按模型迁移逻辑；新增字段按 [工程约定](./development.md#标识配置与开源卫生) 用 serde default。保留当前 provider UUID 账户的读法，是让本版本已落地数据可继续使用，不等于重建历史迁移框架。
- 启动不再无条件运行旧 `migrate`。发现当前 v2 明文时，调用同一准备/提交协议：成功才发布新的引用；失败不复制/重写这份明文配置，保留可恢复原件并显式提示“已有配置含未安全存储的凭据”。不能声称历史明文已被清除。任何会重新序列化这份明文的配置写入（包括字体）都必须先完成安全存储，否则阻止该持久化并说明原因；避免从旁路重新制造明文副本。
- 首次安全整理中的 Windows 备份要专项处理：通用写入器对既有明文创建 `.bak` 会制造额外副本。凭据整理应使用不复制含密钥旧内容的配置专用替换器，并测试失败可恢复性；不泛化修改所有历史文件写法。
- 回滚分两类：提交失败自动保持旧引用；已成功提交后的版本回退必须使用理解 `credential_ref` 的已修补版本/前向修复。旧二进制忽略新字段后可能回读陈旧 `provider.id`，因此不支持直接降级至不认识引用的版本；发布说明必须明确，不能为了兼容旧程序双写旧账户而重新打开半提交窗口。保留恢复快照只含已清理的占位/引用，不新增明文“备份”。
- 所有配置写入进入同一串行器后，再用 [R10](#r10-即时子代理模型设置与页级草稿隔离) 的字段所有权与版本检查拒绝陈旧覆盖。单纯互斥只能排序，不能发现旧客户端快照。超时后用户不能假设未提交；用操作 id 查询/刷新提交结果后决定重试。提交意向同时保存不含秘密的提交回执（operation id、版本、已提交引用、后处理阶段），配置中记录本次 operation id 以便崩溃后对账；已完成/不确定的同 id 不自动再次执行清理，返回已提交快照及后处理状态。回执过了保留窗口则明确结果未知、要求重读核对，不能当作新操作盲重放。
- 秘密值不作为错误、日志、指标、测试快照或哈希指纹输出；内存暂存最短生命周期，避免 `Debug` 打印。崩溃转储/操作系统层内存防护不在本次“不落配置明文”的保证之内。

### 测试与验收

用临时目录、确定性假钥匙串、假文件写入器和阶段屏障测试，默认测试不访问真实用户账户。拟在 `config_commit` 下建立如下矩阵，覆盖真实命令接线而不只测纯辅助函数：

| 用例 | 注入点/输入 | 必须观察到的结果 |
|---|---|---|
| 首次新 key | 正常准备与提交 | 所有捕获到的配置/临时/恢复文件字节均无测试 key；权威快照仅有状态/占位；运行解析得到完整 key |
| 系统拒绝/无服务 | 账户创建、写、读回分别失败 | IPC 返回结构化失败；旧文件、旧有效池、内存版本不变；UI 不显示成功，保留可重试编辑 |
| 文件写失败 | keyring 已准备后写/替换失败 | 旧配置仍解析旧池；新账户不成为生效引用；清理失败可重试且不含秘密 |
| 多供应商 | 第二/最后一个账户失败 | 不出现部分 provider 已生效、部分仍旧值；第一账户只是未引用候选 |
| 崩溃恢复 | 意向前后、每个账户后、提交点前后强制终止子进程 | 重启选择完整旧或完整新引用；当前引用不被 GC；不能以“测试未抛错”替代解析池断言 |
| 当前明文数据 | 整理成功/失败/Windows 替换失败 | 成功后所有新写入仅含引用；失败不新复制明文；启动能看到存储警告 |
| 并发和迟到响应 | 页保存/字体/技能/角色/命令白名单交错 | 无丢字段、旧响应不能回退 store；“始终允许”只 patch 去重白名单，操作 id 重放不重复副作用 |
| 运行中清空凭据 | 旧 ModelConfig 已捕获，清空后触发该调用 retry，再建立新请求决议 | 旧快照按既有边界可继续且账户未提前 GC；新配置决议为零 key，不声称清空撤销了在途调用 |
| 真平台 | macOS、Windows、Linux 有/无 Secret Service、锁定/用户拒绝 | 分平台记录成功和失败；假实现通过不计为系统钥匙串验收 |

**可执行 AC：** 为上述夹具分别建立 `credentials_never_enter_config_writes`、`failed_file_commit_keeps_old_credentials`、`startup_uses_same_secure_commit`、`partial_prepare_never_publishes`、`restart_preserves_referenced_accounts` 等命名回归；在 `src-tauri/` 执行 `cargo test --workspace config_commit` 后执行全量后端门禁。前端以延迟/拒绝 IPC 验证成功文案与 store 内容，执行 `pnpm --dir ui test`、lint、build。最终三平台人工按“假测试凭据保存 → 重开 → 锁定钥匙串再保存 → 检查旧配置仍可用/错误可见”验证，不用真实密钥做截图或故障注入。全部满足后才能把 SECURITY 中的现存明文限制改为新保证及其范围。

## R02 追加密钥必须保留已存池

### 场景与证据

供应商已有 keyring 池 A、B，用户在设置中保留 `__keyring__` 并另加 C。预期是 A、B、C；当前迁移却把该供应商账户写成仅 C。用户可能无感丢失原轮换池，导致额度分摊、健康冷却与后续鉴权行为改变，且界面本来就没有旧 key 全值可供恢复。

- **静态事实：** [`ProvidersPanel` 密钥输入](../ui/src/features/panels/ProvidersPanel.tsx#L292-L305) 逐行保留编辑内容；[`SettingsPage.save`](../ui/src/features/panels/SettingsPage.tsx#L847-L854) 只 trim/过滤空行，注释明确保留掩码和占位。[`unmask_from`](../src-tauri/src/core/config.rs#L609-L632) 对不是 `***` 开头的占位原样保留。
- **关键写链：** [`migrate`](../src-tauri/src/host/keyring.rs#L33-L53) 从当前 `keys` 过滤掉占位，直接 `set_password(plain.join("\n"))`，没有读取旧账户。这足以推出输入 `['__keyring__','C']` 会原位写入 C；不需要假定下标错乱。
- **反证：** [`resolve_keys`](../src-tauri/src/host/keyring.rs#L63-L106) 以及 [`resolve_provider_keys`](../src-tauri/src/host/keyring.rs#L124-L143) 的读取确实会合并明文与钥匙串值去重；但保存调用 `migrate`，不是这两个读取入口。不能把读取期合并当作保存期保留的保证。
- **验证状态：** 源码链路已核验；未操作真实 keyring 验证 A/B/C，现有 roundtrip 测试不是追加回归。清空 keys 时现有解析返回空（不复活旧账户）是必须保留的反向约束。

### 目标与设计

**目标：** “保留、追加、整池替换、清空”具有可测试且不依赖可见掩码碰巧匹配的明确语义；重复提交不重复 key；保留请求遇到回读失败就阻止提交，绝不静默把它当空池。非目标是逐枚旧 key 的查看、导出、独立删除/命名以及修改 KeyPool 冷却算法。

与 R01 共用 `CredentialEdit` 归一层和不可变账户提交，不单独再维护一套迁移逻辑。推荐前端表单将“已保存密钥”显示为状态行，输入框只容纳本次新输入；命令 DTO 携带每 provider 的明确意图：`keep`、`append { new_keys }`、`replace { new_keys }`、`clear`。空 `append` 可归一为 `keep`；空 `replace` 必须按显式清空意图处理，不靠丢了占位行猜测。R01 返回脱敏的 `configured`/数量（数量可取决于安全可读状态），不回传真实旧池。

处理规则：

1. `keep` 保持后端当前凭据引用，不需读取或重写系统账户。除非 R01 发现当前仍有明文、该次配置写必须先安全整理。
2. `append` 在锁内读取被保留的**当前完整池**；旧池读取失败返回 `CredentialReadFailed`，所有新写均不开始。按“旧池原顺序 → 新输入顺序”稳定去重，不排序、不改变 key 大小写，首个 key 的选择和额度统计保持预期。新输入 trim 并过滤空行，拒绝内部换行/保留哨兵作为真实 key。
3. `replace` 只保留用户明确输入的新池；可以不要求旧池可读，因为用户明确要求替换。产生新的版本化账户，不覆盖旧账户。`clear` 解除已提交配置中的引用，新配置/新请求决议解析为零 key；不从旧账户补回，已捕获的旧请求快照不在此撤销保证内。
4. 新客户端不以 `***abcd`、`__keyring__` 字符串表示编辑意图。为单次发布的当前入口切换保留一个受测的内部适配层：含占位+新行 → `append`；仅占位 → `keep`；无占位的完整新值 → `replace`；无行 → `clear`。先按 current provider id 解掩码；无法匹配的掩码返回可恢复冲突，不能继续把它静默丢弃后覆盖整池。保留哨兵只能引用已经存在于该 provider 的当前状态，新 provider 携带哨兵直接拒绝。
5. 输入 payload 与持久化 DTO 分离。后端验证 provider id 唯一、意图没有重复/未知 provider，禁止把另一供应商凭据引用抄入本项。对相同后缀的掩码碰撞不“任选第一枚”；推荐直接退出字符串掩码编辑协议，而不扩大现有末四位匹配的职责。

**取舍：** 简单补 `migrate` 的 `read + concat` 可以快速覆盖 A/B/C，但仍含“缺占位到底是删除还是替换”的歧义，也不能处理 R01 文件失败和原位半提交。本方案保留现有池的整体管理粒度，仅显式化意图，UI 与 IPC 改动比局部补丁大，但安全边界可以一次测清。若分阶段发布，第一阶段只能作为受限止血：读失败绝不写、先合并再交 R01 的安全提交器，不能再独立写旧账户。

### 兼容与边界

- 当前 provider UUID 账户的已有池在首次真实变更时读入新 generation；未编辑时不做无意义重写。不会把旧 schema v1 或模型账户历史迁移重新引入。
- 追加顺序明确采用旧优先。当前混合读取是明文优先（[`resolve_keys`](../src-tauri/src/host/keyring.rs#L71-L94)），因此安全整理已有“占位+明文”配置时要保留其已生效顺序；与新 UI 的“追加到末尾”意图分开处理，不能用同一个默认 concat 顺序悄悄改变存量首 key。
- `append C` 重试幂等；同一保存操作使用同一 operation id 不重复提交；不同操作追加相同 C 也经稳定去重。两个客户端以同一旧版本追加时，先到者成功，后到者收到冲突并刷新后重算，不能原位最后写者获胜。
- 旧池读取失败不允许根据新输入“猜测旧池为空”。`replace` 和 `clear` 可以作为用户明确选择的恢复路径；界面必须解释会替换/清空已存池，不能替用户自动选它们。
- 清空凭据是后端契约；当前 UI 的至少一把 key 验证另有产品限制（[供应商与网络](./providers-and-network.md#1-配置模型与保存边界)）。本项不以修复追加为由擅自开放无认证端点；可让用户通过删除供应商清除，或在单独批准的 UI 设计中开放清空。若加入“清空”按钮，需同步校验策略和说明。
- 物理凭据删除/孤儿清理遵守 R01 延迟回收；清空后新读取的已提交配置及基于它的新请求决议解析为零 key；已持有旧快照/凭据的请求或轮次按既有边界结束，其 retry 仍可能使用该快照（[`drive.rs`](../src-tauri/src/core/agent/drive.rs#L1516-L1535)），不承诺即时撤回。如要强制撤销须另行定义取消运行与每次请求校验凭据代际的语义。回滚新表单不能回滚到过滤占位后原位写入的旧迁移实现。

### 测试与验收

| 原有状态与操作 | 预期已提交池/失败行为 |
|---|---|
| 旧 A、B，append C | 恰为 A、B、C，旧优先且新旧都可解析 |
| 旧 A、B，append B、C、C、空白 | 恰为 A、B、C；重复保存同结果 |
| 旧 A、B，keep | 原引用不变、零 keyring 写入 |
| 旧 A、B，replace C | 恰为 C；不意外保留 A/B |
| 旧 A、B，clear | 新提交配置解析零 key；旧账户存在也不能补回配置引用 |
| 清空时旧请求快照尚在，随后 retry | 旧轮次按既有边界结束；新配置决议无 key；旧账户不提前 GC，两者不混作即时撤销 |
| 旧账户丢失/锁定，append C | 整体失败，不覆盖为 C、不创建生效引用 |
| 旧账户丢失/锁定，明确 replace C | 按 R01 准备与提交成功后仅 C |
| 两 provider 同名/两个 key 同末四位 | 按 provider id 隔离；未知/歧义掩码拒绝，不串池 |
| 当前明文、占位混合、仅占位、新 provider | 转换规则确定，保留存量生效顺序，非法哨兵拒绝 |
| 两追加并发、文件失败、提交后响应丢失 | 冲突可见、旧池不丢、操作 id 对账后可重试 |

**可执行 AC：** 补 `append_preserves_existing_pool`、`append_read_failure_never_overwrites`、`replace_and_clear_are_explicit`、`mixed_current_data_keeps_effective_order` 等 Rust 用例，使用 fake keyring 断言调用顺序和最终引用；在真实保存入口经 DTO 执行，不能只对手写数组 concat 做单测。`providers.panel.test.tsx` 验证表单显示保留状态、追加/替换载荷、取消零提交、错误保持新输入；现有 provider 验证/弹框测试继续通过。执行 R01 的跨层回归和最终 `pnpm prepr`。人工使用专用测试账户完成 A/B → 追加 C → 重开 → 替换 C → 清空/删除，逐步确认池数量和测试端点行为，截图不包含真值。

### 实施安排

1. 先补 A/B/C 与回读失败的保存入口回归，确定稳定顺序；冻结 `CredentialEdit` 载荷。
2. 后端归一、去重与校验接入 R01；同步前端已存状态与新输入分离，去掉占位符作为可编辑秘密的显示方式。
3. 验证读取侧标题/压缩/额度和池选择均使用同一引用，更新长期密钥编辑契约。

**依赖与估算：** 依赖 R01 的安全提交骨架，不能抢先交付原位写新池；预计额外 1–2 工程人日（不重复计 R01 基础设施），另有人工平台时间。风险集中在取消语义、已有混合池顺序和第三方直接调用旧 IPC 的行为。未决：是否在本期开放逐枚管理或无 key 供应商；建议均不纳入，后续单独决策。

## R03 Office 修改与还原必须先完成备份，再覆盖目标

### 场景与证据

用户编辑现有 `.xlsx/.xlsm/.docx`，或在文件面板还原旧版本时，备份目录不可写、磁盘空间不足、当前文件无法完整读取，都可能导致“目标已经改变，但没有可恢复的改前版本”。修改工具仍返回成功并显示“已保留原件备份”，会让用户在错误保障下继续修改，最终失去唯一原件。严重度保持原报告 P1；因涉及原件保护，建议纳入先行数据安全批次。

本节证据来自基线 `8df75db5e9aeb6e9830892fba0e54ddd63856a9b` 的静态读取，未执行故障注入、真实 Office 打开或 GUI 验证；下面测试均为待实施验收，不是本次通过记录。

- Word 收尾把读取失败降为 `None`，备份失败只记日志，随后仍 `atomic_write`，最后无条件加入“已保留原件备份”：[`edit.rs:235–275`](../src-tauri/src/tools/document/edit.rs#L235)。表格路径重复同样逻辑：[`edit.rs:729–782`](../src-tauri/src/tools/document/edit.rs#L729)。成功结果里的 `backup` 实际可以是 `null`。
- 还原路径同样用 `read(target).ok()` 和 `backup::save(...).ok()` 吞掉错误，然后覆盖目标：[`preview.rs:162–190`](../src-tauri/src/host/commands/preview.rs#L162)。已有目录边界校验有效，不能把它描述为“完全没有校验”；缺口是事务前置条件和错误语义。
- `backup::save` 的注释明确鼓励失败后继续，实际使用普通 `fs::write`，写完即修剪到五份：[`backup.rs:58–67`](../src-tauri/src/tools/document/backup.rs#L58)。占名检测是 `exists → write`，不是排他创建；“原子目标写入”不等于“备份已完整持久化”。
- 反证与范围：ZIP 重打包已经保留未改成员并检查 `finish/flush`：[`patch.rs:90–131`](../src-tauri/src/tools/document/patch.rs#L90)。目标原子写也已有临时文件和 `sync_all`：[`atomic.rs:7–36`](../src-tauri/src/util/atomic.rs#L7)。本问题不应误写成直接写半包，亦不能通过整份解析重建 Office 文件来解决。
- 但该原子写 helper 不能原样复用为安全保证：Windows 分支用固定 `target.with_extension("bak")`，忽略 copy 错误，成功/失败最后都删除这个路径，persist 失败还会尝试从它回写：[`atomic.rs:16–34`](../src-tauri/src/util/atomic.rs#L16)。这可能覆盖/删除用户已存在的同名 `.bak`，copy 失败后也可能把不属于本次操作的旧 `.bak` 回写进目标。此风险必须在接入公共事务前修复，不仅留作“专项回归”。
- 虚假保证直接进入 `warnings`，主要影响 UI；模型侧序列化的是 `outcome.data`，不含 warnings：[`compact.rs:42–54`](../src-tauri/src/tools/compact.rs#L42)。准确结论是“成功回执与备份保证不一致”，不能断言模型必然看到了那一句提示。现有成功路径备份/还原测试不能反证失败路径安全：[`edit.rs:1030`](../src-tauri/src/tools/document/edit.rs#L1030)、[`preview.rs:240–283`](../src-tauri/src/host/commands/preview.rs#L240)。

### 目标与设计

**目标**：对已存在的 Office 目标，成功覆盖必有本次实际改前内容的完整备份；任何读取、备份、验证、最终提交失败都不得报告“修改成功且可回退”。工具编辑和 host 还原共用该条件。**非目标**：无限版本库、跨文件 ACID 事务、自动重算 Excel、跨进程强互斥、完整断电一致性认证、改变 Office 保真修改方式。

推荐“失败关闭的文档写事务”，不提供默认或模型可选的 `skipBackup`。与 R04 共用同一路径写锁，否则可能出现“基于 A 生成补丁，备份 B，再把 A 的补丁覆盖 B”。具体数据流如下：

1. 参数及读/写根校验 → R04 的认领策略 → 获取 canonical 目标写锁，持锁后重验目标类型与路径。审批预览不持锁等待用户；真正执行时在锁内重新读取并计算结果。
2. 为现有文件获取一个完整、受体积限制的源快照，记录内容摘要；解析、计划、保真重打包都基于同一个快照，而不是多次从可变目标读不同成员。优先把快照放受管临时文件，沿用 `patch::apply` 的路径接口，避免一次引入全套 Reader API。临时文件失败即停。
3. 新增窄职责的 `tools/document/transaction.rs`（建议模块名）：提供 `prepare_existing` / `commit_prepared` 及 `DocumentWriteError`，持有 `PreparedDocument { source_digest, staged_path, backup_receipt }`。`BackupReceipt` 必须是已完成的非空凭据，不能用 `Option<PathBuf>` 表达“成功覆盖现有文件”。调用方映射统一错误码，host 只做路径校验和转调，不复制事务判断。
4. `backup.rs` 保存采用受控目录内的排他创建或临时文件 + 不覆盖发布，完整 `write_all`、flush/`sync_all` 后校验长度/摘要，才返回备份凭据；失败清理自己产生的半成品。新备份未确认完整时绝不 prune。备份命名和现有列表读取保持兼容。
5. 提交前比较目标与源快照摘要；检测到期间变化则 `E_DOCUMENT_CHANGED` 中止并要求重新读取。先修正 `util/atomic.rs` 的 Windows 安全替换，再接入事务：不得再使用固定 `.bak`；若平台流程需要回滚文件，在目标同目录用唯一、排他创建的受管文件，完整复制并 sync/校验后才标记 `RollbackReady`，复制失败立即中止且绝不进入 persist/回写。仅能从本次已验证凭据回滚，也仅清理本次拥有的临时文件；persist 失败且原目标未变化时不做多余回写。回滚本身失败则保留完整恢复文件、返回 `E_ROLLBACK_FAILED` 并给出实际状态，不能宣称“原件未改”。Windows 安全替换原语及失败是否保持旧目标的实际行为需用平台测试确认；不凭 rename 名称假定。取消在开始提交前检查，提交临界段不插入“已写完却只报取消”的 await。成功提交后才登记产物、生成成功结果和做备份保留清理；修剪不得删除本次凭据或仍被在途还原引用的版本，同文件清理纳入同一事务锁。
6. 统一结果：保留现有 `path/changed/changes/backup`，成功编辑的 `backup` 必为可读路径；可增 `backupStatus: "saved"`。读取失败返回 `E_SOURCE_READ`，备份失败返回 `E_BACKUP_FAILED`，覆盖失败返回 `E_IO`，并在错误消息说明“目标未修改”仅限已验证未提交的分支。备份已成功但目标提交失败时保留备份，错误中可给恢复位置。不得把这些关键事实只放 warnings；失败经 `compact_for_model` 仍必须让模型读到原因。
7. host 还原先读入所选备份并验证受限目录边界，再进入相同事务，确保它不会被保存当前版本的 prune 提前删除。现有 `currentBackup` 保持兼容，存在目标的成功还原必非空。备份目录实际来自 `rt.data_dir/tmp/document-backup`，不是按 session id 隔离；保留实际路径边界，不按错误注释宣称会话级物理隔离。补充验证所选备份确属目标的列表，避免在全局备份目录内误选另一文档。

**不存在目标的还原策略**：建议保留恢复被删除文档的能力，但只在准确的 `NotFound` 情况进入 `MissingTarget` 模式；`PermissionDenied` 等不能冒充缺失。此模式返回 `backupStatus: "not_needed_missing_target"`、`currentBackup: null`，以“不覆盖已有目标”的原子创建提交；并发新建导致 `AlreadyExists` 时拒绝，不降级为覆盖。若不实现可靠 no-clobber 提交，首版必须显式拒绝缺失目标并说明限制，不能继续借用普通 `atomic_write` 冒险覆盖。该产品选择需在实施前定稿。

**取舍与替代**：只把 warnings 改为条件显示只能消除一句误导，无法保护原件；只在两个编辑分支加 `?` 容易遗漏 host 还原，也未解决源快照错位。完整统一文件事务框架牵涉普通 edit 多文件回滚，范围过大；本轮限定 Office 编辑/还原共用的窄 helper。内容摘要新增一次最多 50 MiB 级读取，应记录耗时，不承诺零性能代价。

### 兼容与边界

- 不更换备份目录和旧文件格式，不要求用户迁移历史 `.bak`。现有五份保留策略保留；仅延后清理，并把失败纳入可观察告警。若为目标绑定新增元数据，必须支持旧备份的既有列表及受限目录验证，不能因缺 sidecar 宣称原备份损坏。
- 新增 IPC 可选状态须同步 [`ipc/client.ts:146–151`](../ui/src/ipc/client.ts#L146) 及文件面板失败展示；旧字段保留。只在提交确认后刷新 UI 和提示成功；产物登记失败不能假称文件未写入，也不应自动重放修改。
- 写锁仅协调 CodeWave 内遵循同一锁表的入口；外部 Excel、shell、MCP 不受其约束。摘要复验缩小并检测部分外部改动窗口，但复验后至 rename 仍存在外部写窗口，不将其写成跨进程 CAS 保证。
- 权限变化、symlink 重定向、文件从常规文件变目录、目标消失应在锁内重新判断；不自行扩张写根。Windows 文件占用/rename 失败必须保留原件和持久备份；安全替换必须先移除固定 `.bak` 风险，用户同名 `.bak` 的字节和存在状态全程不受影响。该公共 helper 改动还需回归其普通文件/配置保存调用方，不能只验证 Office；事务临时回滚文件也不能替代持久版本备份。
- 应用崩溃可能留下额外完整备份或受管临时文件，允许后续清理；不能让清理删除尚未验证的唯一原件。对目录 fsync/断电后目录项持久性的跨平台差异独立记录，不把普通 I/O 测试当断电证明。
- 回滚以版本回退为单位，旧代码能继续读备份；回退旧写入逻辑会重开数据丢失风险，故紧急回滚优先关闭编辑/还原入口，保留只读与导出备份能力，而不是静默重新允许无备份覆盖。

### 测试与验收

采用可注入文件操作适配器或局部故障点，不能只依靠 chmod（root/Windows 下结果不可靠）。对 `.xlsx/.xlsm/.docx` 编辑和现有目标还原做参数化矩阵：源读取失败；备份目录创建、打开、写中途、flush/sync/验证失败；临时包失败；目标原子提交失败；成功；取消；并发。

- **AC-R03-1（不覆盖）**：每个提交前故障，调用返回明确非成功码，目标字节 SHA-256 等于调用前，产物登记次数为 0；不出现“已备份/已修改成功”的 UI 或模型结果。拟增测试 `document_backup_failure_keeps_original`，必须同时触达 Word、表格及 restore 的真实调用点。
- **AC-R03-2（可逆）**：正常编辑后 `backup` 可读且逐字节等于修改前内容；还原成功后目标等于选中备份，`currentBackup` 等于还原前内容；再次还原可恢复。拟增 `document_restore_requires_current_backup`，同时测读失败与保存失败。
- **AC-R03-3（不造假）**：对失败和成功 outcome 运行 `compact_for_model`，模型可见失败原因/成功 backup；UI 不用 `ok` 之外的空值猜成功。备份成功、提交失败时明确未完成，并保留备份。
- **AC-R03-4（同一版本）**：用 barrier 控制两次受管写/编辑与还原交错，第二次只能读取第一次提交后的版本或明确冲突，不能拿旧补丁覆盖新内容。注入外部变更在摘要复验前发生，必须 `E_DOCUMENT_CHANGED`；不将该测试外推为所有外部竞态已消失。
- **AC-R03-5（版本库）**：连续六次成功后保留规定数量；备份失败不修剪原版本；在还原最旧版本时，当前版本保存不得令已选择内容不可用。缺失目标分支按最终选择测试 no-clobber 或明确拒绝；目录外、symlink 指向外部、其他目标备份全部拒绝。
- **AC-R03-6（保真与平台）**：重跑现有 `faithful_spike`/patch 样本，未修改 ZIP 成员逐字节一致；Windows 占用文件及 macOS/Linux 权限/空间错误分别执行。交用户人工检查真实 Office 打开、修改、还原和失败提示，不做 GUI 自动点验。
- **AC-R03-7（Windows 安全替换）**：预置目标及用户同名 `.bak`，分别注入回滚复制失败、persist 失败、复制与 persist 双故障配置、回滚失败及正常成功；每例都断言用户 `.bak` 原样存在。复制失败时 persist 调用计数为 0，未验证回滚文件绝不读取/回写；persist 失败时原目标保持或从本次完整凭据恢复，恢复失败则返回真实降级状态并保留恢复文件。同时验证多个相同 stem、不同扩展名文件并发写不会共享临时回滚名。拟增 `document_windows_atomic_preserves_user_bak`，故障适配器单测与真实 Windows 集成均必需。

## R04 统一 Office 文件认领策略与写锁生命周期

### 场景与证据

用户在主会话 A 修改 Office 文件后，另一主会话 B 接手同文件时可能一直收到 `E_FILE_CLAIMED`；反过来，两个 Office 子代理可能同时绕过认领并覆盖彼此内容。定时任务、普通文件工具与 Office 工具的规则也不一致。严重度保持原报告 P1；共享写锁部分是 R03 数据保护验收的依赖，应一并安排。

本节为同一基线静态确认，未实机并发复现，未运行线程/取消/崩溃试验。

- Office 写入使用 `root_session_id.is_none()` 才认领：[`write.rs:327–345`](../src-tauri/src/tools/document/write.rs#L327)、Word 和表格 [`edit.rs:690–717`](../src-tauri/src/tools/document/edit.rs#L690)。普通 create/edit/delete 使用 `!rt.is_main_session`：[`create.rs:60–84`](../src-tauri/src/tools/create.rs#L60)、[`edit/tool.rs:369–389`](../src-tauri/src/tools/edit/tool.rs#L369)、[`delete.rs:66–89`](../src-tauri/src/tools/delete.rs#L66)。
- `root_session_id` 表示产物归属，主会话和计划任务都为 `None`，不是是否主会话的判据；专门的 `is_main_session` 已存在：[`runtime.rs:240–250`](../src-tauri/src/core/agent/runtime.rs#L240)。主会话构造置 true，任务默认 false：[`runtime.rs:441–451`](../src-tauri/src/core/agent/runtime.rs#L441)、[`runtime.rs:626–632`](../src-tauri/src/core/agent/runtime.rs#L626)。因此不能只把 `.is_none()` 翻转为 `.is_some()`，那会漏掉没有父会话的任务。
- 释放守卫只在 `!params.main_session` 时武装：[`drive.rs:829–831`](../src-tauri/src/core/agent/drive.rs#L829)。主会话误认领后没有该正常释放路径。claims 是进程内全局表，冲突保持直到 `release(owner)`：[`claims.rs:13–19`](../src-tauri/src/tools/claims.rs#L13)、[`claims.rs:44–85`](../src-tauri/src/tools/claims.rs#L44)。
- **必要反证**：相同 owner 的重复 claim 是幂等的，所以不能说“同一个主会话下一次必然被自己阻断”。确定影响是其他 owner 的 Office 主会话写，以及遵守普通规则的非主 runtime 写。Office 子代理的 `root_session_id = Some(...)` 会跳过 claim，不会被该表正常隔离。计划任务目前会认领且有释放守卫，并不是所有非主路径都泄漏。
- 已有 `file_ops` 只串行同一 runtime 的批次写：[`batch.rs:213–251`](../src-tauri/src/tools/batch.rs#L213)。全局 `writelock` 已支持同路径、规范化、顺序获取和可取消等待：[`writelock.rs:19–58`](../src-tauri/src/tools/writelock.rs#L19)，但 Office 三条写路径和 host 还原未调用。claims 的任务级语义隔离不能替代一次读改写的互斥。

### 目标与设计

**目标**：Office 与普通文件工具遵循同一运行身份判断；非主 runtime 的文件范围从首次认领持续到 drive 结束并正确释放；所有受管同目标写入串行，真正执行的检查/读取/生成/提交在同一锁周期。**非目标**：让主会话失去共享文件整合能力、改变兄弟任务冲突为重试等待、让 shell/MCP 获得文件沙箱、跨应用文件锁、修改既有权限档位。

推荐复用当前隔离策略，分两层落地，禁止用“所有主会话也认领”修补局部条件而悄然改变产品契约：

1. 在 `claims.rs` 或 runtime 的窄接口定义 `requires_file_claim(rt) = !rt.is_main_session`。`create/edit/delete/write_document/edit_document` 全部消费这一判据；用表驱动测试钉住主会话、一级/嵌套子代理、任务四类。`root_session_id` 继续仅用于归属，不承担写保护身份。
2. drive 的守卫武装使用同一 runtime 判据，增加 `params.main_session` 与 `rt.is_main_session` 的一致性断言/测试，避免两个布尔量日后漂移。必须覆盖实际 `main_drive_params`、子代理和 `run_task_agent` 的构造链，不能只测 helper。
3. 维持顺序 `路径校验 → claim（短临界区）→ writelock → 锁内重新读/检查 → 事务提交`。claims 内部 Mutex 不跨 await 持有；路径锁按已有排序去重，取消时返回 `E_CANCELLED`。冲突仍立即返回 `E_FILE_CLAIMED`，指明文件/持有者，并要求跳过上报，不能自动重试。
4. `edit_document` 在进入 Word/表格分支前统一取得目标写锁，之后才 load/plan/build；R03 的源快照、备份、原子替换位于该锁内。`write_document` 把 `exists` 检查移入锁内，直到最终创建完成才释放；提交仍须采用原子 no-clobber 创建，不能只靠写前二次检查，把“只新建”变成最后写者覆盖。建议实现通用 `atomic_create_new` 并由两种 Office 生成消费，外部进程在检查后抢占也返回 `E_EXISTS`。
5. host 的 `restore_document_backup` 进入 R03 同一事务/锁，不创建长生命周期 claim，因为是用户直接触发的一次还原；锁等待须有明确可观察状态或有界 busy 返回，不能无限挂起文件面板。若关联主会话取消令牌会误取消手动还原，优先给还原独立的短等待超时并返回可重试 `E_FILE_BUSY`，具体时限作为产品常量由测试固定。
6. ReleaseGuard 在正常结束、错误、取消和 panic unwind 都释放本 owner 全部 claim；不在单个文件写完成后释放，否则同一子任务稍后第二次写又可被兄弟插入。保持相同 owner 的重复认领幂等、多个路径原子认领、祖先路径冲突。工具参数错误后已获得的 claim 保留到任务结束，延续既有语义，不本轮引入部分 release。

**替代与取舍**：

- 仅补主会话的 ReleaseGuard 可减少泄漏，但子代理继续绕过 claim；只改判断可修身份，Office 写锁缺口仍在，不能宣布并发安全完成。
- 所有 runtime 无差别认领 + 每 run 释放是一种新政策，会让主代理汇总共享文件被子任务阻断，与[现行主会话豁免](./subagents.md#文件认领)冲突，本轮不采用。
- 统一 RAII `WriteAccessGuard` 一并认领/持锁可减少遗漏，但不能让它在单次 tool Drop 时释放任务 claim。若抽象，需要明确两个不同生命周期；首版宁可用一个共享判据和清楚的两行调用，不建立隐藏释放行为。
- 主会话仍豁免语义 claim：它与正在运行的子代理操作同文件时只能保证受管写串行，不能保证业务意图不冲突；任务编排仍应等子任务完成再整合公共文件。这是保留的契约边界，不是锁修复失败。

### 兼容与边界

- claims 无持久化 schema。版本升级正常重启会清空旧进程泄漏表，不做磁盘迁移；若支持热更新，必须先停止/排空任务再清理已确认的旧主 owner，绝不能直接 `clear_all` 释放活跃子任务。无热更新支持时明确要求重启即可。
- `E_FILE_CLAIMED` 对 Office 子代理/任务的出现属于修复后的预期行为，保留现有指名与“跳过上报”文案，模型不会因遇到新错误码而需要迁移。主会话不新增长期认领，结果数据格式不变。
- canonical 处理沿用 pathutil；已有文件的 symlink 别名必须同锁，尚不存在文件按最近存在祖先归一。硬链接、大小写别名、网络盘、外部 symlink 替换不轻率宣称全覆盖，需要专项记录。
- 现有写锁按“相同 canonical 路径”互斥，目录删除与子文件写的祖先关系主要靠非主 claims；主会话豁免下目录级互斥不是本次同文件锁自动覆盖的能力。测试不可拿 claims 祖先冲突结论冒充 writelock 祖先互斥。
- 不在持有路径锁时弹用户确认，不在锁内发网络请求；最长持锁成本是本地 Office 解析/备份/提交。等待取消后不得写文件；同步提交已经开始则返回实际完成结果，不能假报未发生。
- 回滚这一变更无需迁移数据，但回退会重开泄漏/交叉覆盖风险；紧急处置优先禁用非主 Office 写入口并提示主会话处理，而不是移除写锁。R03 不能在缺少该锁的状态下声称事务覆盖了跨 runtime。

### 测试与验收

矩阵主轴为“写入口 × runtime 身份 × 退出方式 × 路径别名”；Office 覆盖 xlsx/xlsm/docx edit 和 xlsx/docx create，混合对手覆盖普通 create/edit/delete 与 restore。

- **AC-R04-1（身份一致）**：主会话 A 完成 Office 写后，主会话 B 与后续子代理可接手；相同 owner 可连写两次；一级/嵌套子代理及独立任务之间相同/祖先路径冲突均按 `E_FILE_CLAIMED` 拒绝，未触及目标字节。拟增 `document_claim_policy_matches_runtime_role`。
- **AC-R04-2（生命周期）**：通过真实 drive 构造模拟成功、Provider 错误、取消、panic/abort，退出后另一 owner 可认领；运行期间不能提早认领。用无真实模型网络的 fake provider/barrier 控制流程，不能只手动调用 `release` 证明生产 Drop 正确。拟增 `drive_releases_document_claims_on_all_exits`。
- **AC-R04-3（互斥）**：用 barrier 在锁内暂停一次 Word/表格写，第二个主会话或 restore 不得进入同目标读改写区；释放后它从最新版本计算。不同文件不互相阻塞。相对/绝对/symlink 路径触发同一把锁；测试必须观测两个修改均保留或明确冲突，不能只断言都返回成功。
- **AC-R04-4（只新建）**：两个主会话同时 `write_document` 同一路径，仅一个成功，另一个 `E_EXISTS`，产物是完整可读文件；外部创建插入 `exists` 与提交之间也不得被覆盖。拟增 `document_create_race_never_overwrites`。
- **AC-R04-5（可取消）**：持有第一把锁后启动第二调用，取消第二调用，断言及时返回 `E_CANCELLED`、没有备份/文件变更，第一调用正常完成；restore 的 busy 超时按其独立契约测试。
- **AC-R04-6（边界）**：进程重启后不恢复旧 claims；多路径失败不部分认领；task 无父 id 仍隔离；R03 注入备份/提交失败后 guard 不泄漏。人工验收两个会话顺序续改和用户还原，不做 GUI 自动点验。

实施后在 `src-tauri/` 运行 `cargo test --workspace claims`、`cargo test --workspace writelock`、`cargo test --workspace document_` 和完整 `cargo test --workspace`；按测试指南执行全部平台对应检查，开 PR 前运行 `pnpm prepr`。测试命名为拟定入口，实施时若调整必须更新命令和实际输出记录。

### 实施安排

1. 写 runtime 身份矩阵及泄漏回归。2. 抽共享判据、替换 Office 分支、统一 drive 守卫判据。3. 接入全局写锁与 no-clobber 创建，与 R03 合并审查事务区间。4. 跑真实调用链生命周期/并发测试并更新[子代理](./subagents.md#文件认领)、[文档工具](./documents.md#5-备份与回退)和[工具安全](./tools-and-safety.md)。

**估算**：独立身份/守卫修复及测试 1–2 人日；Office 锁、no-clobber 与并发验证 1.5–3 人日，其中与 R03 共享部分只计一次。风险是隐含 runtime 测试构造默认 `is_main_session=false`、锁顺序、取消时机和 Windows no-clobber 行为。未决项：restore 等锁产品时限；是否长期把两个 main 标志收敛为单一类型（建议后续重构，不扩大本轮）；目录级主会话冲突是否另立问题（本轮不声称已解决）。

## R05 项目任务写入与启动恢复路径统一

### 场景与证据

用户在已注册项目中创建周期任务，当次进程可见、可执行，重启后列表与调度表却可能为空。文件仍在项目中，界面会造成“任务被删”的错觉；更严重的是无人值守任务不再执行。此项应按数据可发现性缺陷处理，不能以“文件还在”降低优先级。

- 保存通过 `projects::data_dir_by_id(...).join("tasks")`，正常项目落到 `<主目录>/.codewave/tasks`，见 [scheduler.rs:284–294](../src-tauri/src/core/scheduler.rs#L284-L294)。启动恢复却枚举 `projects_root/<entry>/tasks`，没有读取项目发现索引，见 [scheduler.rs:297–342](../src-tauri/src/core/scheduler.rs#L297-L342)。启动装载入口确实调用该函数，见 [scheduler.rs:411–419](../src-tauri/src/core/scheduler.rs#L411-L419)。
- 当前项目发现的权威路径是 `directories.json → <主目录>/.codewave/project.json`，并有既有会话快照自愈，见 [projects.rs:180–229](../src-tauri/src/core/projects.rs#L180-L229)。但不能直接复用 `projects::load` 并承诺可诊断：索引读取/解析失败被吞成空索引，见 [projects.rs:111–116](../src-tauri/src/core/projects.rs#L111-L116)；`project.json` 不可读且无会话引用时会 `index_forget`，见 [projects.rs:194–207](../src-tauri/src/core/projects.rs#L194-L207)。仅有任务、没有会话的暂时离线项目可能因此失去发现锚点。项目数据路径已有共用解析函数，见 [projects.rs:146–163](../src-tauri/src/core/projects.rs#L146-L163)。
- 反证边界：`data_dir_by_id` 在项目找不到时仍回落全局 `projects/<id>`，所以不是所有测试数据都会丢。现有往返测试只给 `project_id: "proj"`，未调用 `save_project` 创建真实项目，正好命中这一回落，见 [scheduler.rs:1326–1351](../src-tauri/src/core/scheduler.rs#L1326-L1351)；该测试不能证明真实项目重启恢复正确。cron 恢复测试也使用相同形态，见 [scheduler.rs:761–787](../src-tauri/src/core/scheduler.rs#L761-L787)。
- 本次结论来自基线 `8df75db5e9aeb6e9830892fba0e54ddd63856a9b` 的静态调用链复核；未运行修复、应用重启、GUI 或真实定时执行实验。[运行与调度](./runtime-and-scheduling.md#已核实的持久化缺口) 已明确记载该缺口。

### 目标与设计

目标：同一个有效项目的任务保存、恢复、更新、删除与日志使用同一项目数据路径；恢复不删除任务文件；单项目损坏不阻断其它项目。非目标：扫描用户磁盘寻找项目、搬迁旧全局任务、恢复已删除的旧项目 schema、为临时任务增加跨重启保存、自动搬动项目主目录变更前的数据。

推荐实现：

1. 先在 projects 模块抽取与当前发现规则同源、非破坏的 `load_report(data_dir)`，返回有效 entries、保留的发现引用与分项 issues；区别索引缺失、读取失败、解析失败，以及单项目离线/权限错误/坏元数据，失败不能当空索引，也不能因暂时读不到项目而自动 index_forget。现有 `projects::load` 保持返回 Vec 的兼容签名，但内部也必须委托这份非破坏报告，供 [`list_projects`](../src-tauri/src/host/commands/project.rs#L5-L10) 等既有调用消费；否则界面刷新仍能擦掉调度恢复所需的索引。删除发现锚点只由显式项目删除，或单独确认永久失效后的修复入口承担，不能由普通读取推断。会话快照自愈候选复用同一解析逻辑，允许显式补回确认有效的索引，但不得以读取任务为名擦除锚点。调度恢复消费该报告的 entries 与 issues，对有效项使用 `project_data_dir(data_dir, &entry).join("tasks")`。只枚举普通 `.json` 任务文件；忽略临时文件、目录，任务文件符号链接默认拒绝，项目主目录本身的合法符号链接按统一路径规则解析，不能追到任务目录外。不要另抄 `directories.json` 格式，更不要同时扫描旧全局位置“兜底”。
2. 返回内部 `TaskLoadReport { tasks, issues }`，问题至少区分项目不可读、任务不可读、JSON 错、非法 id、文件名/id 不符、`project_id` 与所属目录项目不符、重复 id。单坏文件跳过并保留，错误只包含受影响 id/路径/原因，不输出任务指令全文。重复 id 冲突应隔离冲突任务而非最后写入者覆盖；任务表仍按全局 task id 查找。
3. 任务持久化/删除也改用基于非破坏发现报告的严格 `resolve_task_project_dir → Result`，区分项目不存在与暂时不可读，禁止写入 fallback 路径；不能继续通过 `project_data_dir_by_id → find → load` 绕回会自动忘记索引的旧读链。不要顺手修改所有其它模块对 `data_dir_by_id` 的行为；先把 scheduler 的保存、删除、日志统一到任务专用解析入口。无 `project_id` 的内存任务仍允许，但返回或文案明确不可持久化。
4. 把 `persist` 从静默 best-effort 改为可观察结果；`upsert/update/set_enabled/remove` 的成功回执必须区分内存成功与持久化成功。推荐对用户编辑采用“准备新快照 → 原子落盘成功 → 发布内存”的提交语义，失败保留旧值；后台结果落盘失败保留内存结果并报告未保存，具体执行收尾与 R09 共用。IPC 与 `scheduled_task` 工具同步传播错误，不能继续无条件宣称“挂项目的任务已持久化”，当前文案见 [scheduled_task.rs:104–107](../src-tauri/src/tools/scheduled_task.rs#L104-L107)。
5. 启动导入使用专用 `restore`，不要通过普通 `upsert` 无条件重写全部已读文件；需修正 cron 时间或补写恢复状态时才显式保存。给初始化设置 `Loading/Ready/Degraded` 状态，启动恢复完成前创建/编辑请求等待或返回清晰“正在恢复”，防止恢复覆盖刚创建的任务；坏条目可使初始化为 Degraded，但不能伪装空表成功。

取舍：只改扫描循环是最快的止血方案，但仍会把未知项目写进旧路径、把权限错误当成功，也掩盖损坏文件。推荐把严格路径、真实布局测试和最小错误回传一起交付；数据库/独立任务索引与自动发现 watcher 均不纳入本轮。

### 兼容与边界

- 只读写当前布局；**不新增旧全局目录双读、搬迁或旧 schema 迁移**。现存当前格式任务无需迁移，补充字段均使用 serde default；旧位置残留可诊断但不自动加载、删除或复制。
- 项目主目录编辑本来不搬运旧托管目录，见 [会话与项目](./sessions-and-projects.md#项目编辑不能丢权限)。任务只跟随有效注册表位置恢复；目录离线/权限不足应显示诊断，不能新建空目录覆盖事实。完整“离线项目热插拔自动恢复”不是本轮保证。
- 删除项目与保存/执行须协调：R06 的任务操作协调锁为写入串行化入口；项目删除先关闭该项目任务接纳、失效 pending，再删除托管数据，迟到完成不得重新 mkdir。不要持任务表锁调用会修改索引的项目发现逻辑，也不要在表锁内做文件 IO。
- 数据级回滚无需转换，因为任务仍在当前目录；代码回退到旧恢复器会再次漏载，属于已知功能退化。回退前停止调度并备份相关托管数据，不以删除新文件“回滚”；R09 新一次任务状态与恢复器应作为同一发布单元考虑。

### 测试与验收

自动测试矩阵：

| 条件 | 必须断言 |
|---|---|
| 两个真实项目，其主目录在全局 data_dir 外 | 经 `save_project → upsert → 新 TaskTable → restore`，任务、enabled、next_run、runs 全量对等，且全局旧任务根未被创建 |
| 仅有全局历史目录残留 | 不被当作当前项目任务恢复，不进行自动搬迁/删除 |
| 坏 JSON、错 project_id、错文件名、重复 id、非 JSON 文件 | 不执行不归错项目；保留原文件；其它健康项目仍恢复；诊断可定位 |
| 主目录离线、权限拒绝、磁盘写失败 | 创建/编辑不报持久化成功，不回落全局，不静默擦除旧任务/索引 |
| 已注册项目只有任务、没有任何会话；离线期间实际 list_projects 与任务恢复并发，再恢复目录 | 离线加载返回可定位 issue，directories.json 字节不变；恢复原目录后再次加载仍发现任务 |
| directories.json 不可读或损坏 | 明确 index issue；不伪装健康空列表、不以空索引覆盖原文、不改扫旧布局 |

## R06 排队任务执行前复核与单次认领

### 场景与证据

任务 A 长时间持有全局执行锁，任务 B 到期进入 pending。用户暂停、删除 B，或把 B 改到明天；A 结束后 B 仍按旧指令执行。任务以 FullAccess 运行，因此这不只是错误提示，也可能造成用户已经撤回的命令/写操作真实发生。

- `tick` 在表锁内只检查当时的 enabled/next_run，然后返回整个任务克隆，见 [scheduler.rs:350–401](../src-tauri/src/core/scheduler.rs#L350-L401)。supervisor 对每项 spawn，`run_task` 等 `exec_lock` 后直接执行旧快照，见 [scheduler.rs:421–439](../src-tauri/src/core/scheduler.rs#L421-L439)。
- `set_enabled/remove/update` 能修改/移除表中的任务，但没有失效已经排出的克隆，见 [scheduler.rs:194–281](../src-tauri/src/core/scheduler.rs#L194-L281)。`run_task_locked` 在再次读取任务之前就发 fired 并登记等待目标，见 [scheduler.rs:477–494](../src-tauri/src/core/scheduler.rs#L477-L494)。
- 反证边界：tick 之前已暂停的任务确实被跳过；手动立即运行抢锁失败会报忙且不排队，见 [scheduler.rs:442–460](../src-tauri/src/core/scheduler.rs#L442-L460)。现有 `tick_skips_disabled_tasks` 覆盖的是扫描前暂停，不是等锁期间暂停；不能用该通过记录反驳 pending 竞态。运行已开始后的“暂停”本来不等于取消正在执行的 run，本方案不偷偷改变这条语义。
- 本次为静态证据；没有实际启动 LLM、占锁实验或 GUI 复现。

### 目标与设计

目标：真正获得执行资格前，以当前任务状态原子裁决；暂停/删除成功发生在认领之前时，旧 pending 必须零执行、零 fired、零运行记录；同一任务不因多次 tick 堆积多个旧快照。非目标：增加并发执行、分布式 exactly-once、取消已经开始且可能产生副作用的运行、修改 FullAccess 权限产品设计。

推荐将“发现到期”与“认领执行”拆开：

1. 内部候选 `DueCandidate { task_id, generation, scheduled_for }` 只带身份，不携带可执行指令。每任务维护内存 generation 与 pending/running 标记；创建、编辑、启停、删除均使旧候选失效。generation 不要求落到公共 JSON，避免无意义持久化协议升级；任务运行记录另用 R09 的 run_id。
2. `collect_due(now)` 在短任务表锁内验证 enabled/到期/表达式有效，并只为无 pending/running 的任务登记一个候选；此阶段不提前推进 next_run、不删除 once、不发 fired。supervisor 仍全局串行，但 pending 数量上界为任务数，不能每 15 秒无限 spawn 同任务。
3. 获取 `exec_lock` 后进入 `claim(candidate, actual_now)`：重新验证存在、generation 一致、enabled、next_run 与候选相同且确已到期；解析失败先隔离并诊断，不能将非法任务先放进 due 再执行。失败则仅清理该候选，不能清掉新 generation 的 pending。成功从当前实体生成不可变 `ExecutionSnapshot`，推进循环任务到 actual_now 之后的下一次，once 将 next_run 清空但保留实体，并写入 R09 的 `active_run`。必须提交成功才发 fired、注册 wait target、调用运行内核。
4. 对任务变更与持久化增加统一短事务协调入口，例如 `mutation_lock`。固定顺序：执行路径 `exec_lock → mutation_lock → tasks`；编辑/启停/删除只取 `mutation_lock → tasks`，永不反向等待 exec_lock。表锁仅作快照/提交，释放后才 IO；mutation_lock 可跨一次原子磁盘提交，不能跨 LLM/网络运行。关键认领写失败则不执行，保持可重试状态并暴露失败；不能只用“释放表锁后随意 persist”导致旧快照晚写复活新状态。
5. UI 手动运行保留“paused 也可手动跑、不修改 next_run、忙则拒绝”的现行契约。`trigger_now` 改为先拿 try_lock，再在同一认领入口检查当前实体并抓取快照，source=manual 不检查 enabled；删除已完成则报不存在。不得先克隆、后抢锁、再盲用克隆。
6. `finish_run(task_id, run_id, result)` 与 R09 合并为一次状态提交；只结算该 run，不覆盖运行期间用户编辑的新名称/指令/计划，不复活删除实体。运行期暂停只阻止之后的定时认领，当前 run 仍可收尾记真实结果。

取舍：仅在拿到执行锁后检查 enabled/id 能止住一部分误执行，但无法区分“暂停后又启用”“改计划”“删除重建同 id”及重复 pending，且 tick 已推进 next_run 导致不能直接重验 due。推荐候选+generation+认领整体修复；为每个 pending 仅加 cancellation token 可作为实现细节，不能取代临界区内的身份校验。

### 兼容与边界

- 循环任务排队期间不再积累每个错过周期，推荐合并为一次实际执行，next_run 从实际认领时间计算；这是需要明确记录的行为选择。继续保留 cron 本地时区与 DST 规则，不增加补跑队列。
- 可观察线性化点是认领提交：暂停/删除先返回成功则后续绝不启动旧候选；认领先完成则允许当前 run 收尾，界面应显示“已暂停后续运行，当前运行继续”。不承诺能撤回已经发出的外部操作。
- pending 等待中应用退出不记成功；重启按磁盘 next_run 和 R09 的恢复策略决定。项目删除须先关闭任务接纳并失效候选；项目缺失仍按 skipped 处理，禁止 fallback 执行或重建目录。
- panic、运行子任务 JoinError、取消、事件发送失败都必须释放 exec_lock、pending/running；清理 RAII 只清同一 run/generation。事件丢失由权威列表里的运行摘要对账，不以事件到达作为执行成功依据。
- 本节 generation/pending 是内存态，无须迁移；共同引入的 active_run/run_id 兼容与降级约束见 R09。回滚须在停止 supervisor、等待/明确终止已有任务后进行，不能在有 pending 的进程中热切回旧逻辑；不要用重启时自动重放来弥补未证实的运行结果。

### 测试与验收

以注入假执行器、可控时钟、Tokio barrier/oneshot 精确控制顺序，不能靠 `sleep(100ms)` 猜竞态：

| 顺序/场景 | AC |
|---|---|
| A 持锁；B 到期；暂停 B 成功；释放 A | B 执行计数、fired、wait 注册、runs 增量都为 0 |
| 同上改为删除 B 或改 B 到未来 | 旧指令执行 0 次；删除实体/文件不复活；新计划保留 |
| B pending 时 pause→enable | 旧 generation 不执行；仅新 next_run 到期才可认领 |
| 同 B 连续 10 次 tick、多个 due 任务 | 每任务最多一个 pending，任一时刻执行数≤1，按确定性 due 时间/id 排序可测试 |
| 认领已提交后暂停/编辑 | 当前只跑一次旧执行快照；结果关联原 run，新计划/用户字段不被 finish 覆盖 |
| 手动 paused、手动忙、手动和删除竞态 | paused 手动可跑；忙不入队不改 next_run；删除先提交则不能启动 |
| claim 落盘失败、非法表达式、项目删除、panic | 无未授权启动；锁/标记最终释放；后续健康任务可继续 |

实施后在 `src-tauri/` 跑 `cargo test --workspace core::scheduler`，再跑 workspace；前端跑 tasks store/page/ProjectNav 用例以及完整 test/build。人工清单：让安全测试任务 A 等待，排入 B，分别暂停、删除、改期 B，待 A 结束确认无启动；明确使用无真实副作用的 fixture，不让用户拿生产任务验证。所有这些验收本次均未执行。

### 实施安排

依赖 R05 的严格路径和可观察写入结果，与 R09 共用 claim/finish，建议同一调度器改动批次开发，避免先保留 once 实体却没有防重。步骤：时序红例 → 候选/代数/写入串行化 → 手动入口合流 → 清理与事件/列表对账 → 并发回归。

## R07 异步图片附件绑定原草稿，并在提交时原子合并

### 场景与证据

在会话 A 粘贴、拖入或选择较大图片，读取未完成时切到 B，图片可能进入 B，随后被发送到错误对话；同一会话连续导入两批，后完成的请求会用旧 `images` 快照覆盖先完成的图片。读取期间删除图片、发送清空或关闭 Tab，也可能发生旧内容复活。严重度保持原报告 P1，存在跨会话内容误发送风险。

本节静态核实于同一基线，没有执行 FileReader 延迟模拟或 GUI 操作；从代码可证的目标/快照竞态与待验收的关闭/发送交错分开记录。

- `pushImages(base, items)` 从传入快照构造整个 next，再 `setImages(next)`；剪贴板逐图 await 后使用旧 `images`：[`useComposerAttachments.ts:72–118`](../ui/src/features/chat/useComposerAttachments.ts#L72)。路径入口经过目录授权和 base64 IPC 后亦使用同一个旧快照：[`useComposerAttachments.ts:125–159`](../ui/src/features/chat/useComposerAttachments.ts#L125)。
- Composer 注入的是未经会话绑定的 `setDraftImages`：[`Composer.tsx:70–76`](../ui/src/features/chat/Composer.tsx#L70)、[`Composer.tsx:135–145`](../ui/src/features/chat/Composer.tsx#L135)；store 省略 sessionId 时在真正调用时读 `activeKey`，不存在的桶还会被自动创建：[`run.ts:820–825`](../ui/src/stores/run.ts#L820)。这两点分别导致串会话和旧快照覆盖。
- **反证**：路径读取和目录授权已经捕获 `sessionId`，非图片 `onRefs` 也显式传 `tab?.key`；不是所有附件路径都读取了错误会话。现有每 Tab 独立图片桶与同步切换测试有效，但测试先直接 set 图片再切 Tab，没有让 FileReader/IPC 悬挂：[`composer.per-tab.test.tsx:144–155`](../ui/src/__tests__/composer.per-tab.test.tsx#L144)。
- `dispose` 删除 drafts，`clearDraft` 清除 text/images/refs，当前 setter 的防御创建允许迟到回调重建桶：[`run.ts:527–532`](../ui/src/stores/run.ts#L527)、[`run.ts:838–846`](../ui/src/stores/run.ts#L838)。因此仅给 setImages 补一个 sessionId 不足以关闭所有生命周期竞态。
- 发送另有不能遗漏的窗口：[`Composer.tsx:471–479`](../ui/src/features/chat/Composer.tsx#L471) 先 await `send`，受理后无条件 clearDraft；[`run.ts:623–640`](../ui/src/stores/run.ts#L623) 的受理等待可以跨越用户继续输入或附件读取完成。若新内容在发送快照之后、受理之前进入原草稿，既未出现在已发 payload，又被清空。这不是简单令牌失效能解决的，必须改为只消费本次实际发送快照。

### 目标与设计

**目标**：每次异步导入始终对应发起时的会话和草稿代次；图片追加用提交瞬间的原草稿状态；多批导入不互相覆盖；关闭、主动清空、整份草稿覆盖后，旧请求不能复活图片；发送受理只消费已发送快照，不丢弃等待受理期间新增的未发送内容。**非目标**：更换图片传输协议、增加张数/体积预算、让纯图片消息自动可发送、重构全体 Composer、改变非图片原地引用契约。

推荐“显式目标 + 原子 append + 失效代次”，保留现有同步 setter 兼容其他调用方：

1. 在 run store 建立只存在内存的 `DraftTarget { sessionId, instanceId, attachmentEpoch }`。`instanceId` 每次 Tab 初始化/恢复分配新值，关闭再打开相同 session id 也不同；`attachmentEpoch` 在用户主动清空、整份图片覆盖、历史召回/消息修改等意图替换边界递增。切 Tab 和普通文本输入不递增，用户删除单张图也不作废其他在途导入。发送受理改为下面的快照消费，不复用会使所有在途导入失效的 clearDraft。
2. store 新增 `captureAttachmentTarget(sessionId): DraftTarget | null`、`appendDraftImages(target, items): AppendResult`。目标参数必须显式，接口不允许回落 activeKey。一次 zustand `set` 里验证 Tab 实例/代次、读取当前 images、计算限额、追加；关闭或代次失效返回 `{status:"stale"}`，绝不重建草稿桶。附件状态仍在顶层 drafts，瞬态令牌放并行状态，不塞入持久化 DTO 或高频 timeline。
3. 把 `IMAGE_MAX_COUNT=4`、单图 5 MiB、base64 总长 20 MiB 的常量及纯合并算法移到共享附件策略模块。读取前检查已知 size/MIME，提交时对当前数组重新检查 count/总量。为降低语义变化，首版保留现有“按剩余张数截取本批；若合并后的 base64 总量超限则整批新增项拒绝、已有图片不动”，并明确返回 accepted/rejected/reason。限制适用于最终提交状态，不能因两个请求分别预检都通过而突破总预算。
4. `useComposerAttachments` 不再持有用于写回的 `images` base，不接受可隐式写当前 Tab 的 setter。`addImageFiles`/`addPaths` 显式接收或在同步入口捕获 target，整个 await 链只传此令牌。图片对象 id 在提交前稳定生成一次，store reducer 保持纯计算；message.warning 在 reducer 外根据 `AppendResult` 发一次，避免渲染/重放导致重复弹提示。
5. 原生选择框的令牌必须在 `selectDocumentFiles()` 前捕获，而不是选择框关闭后捕获：现有入口位于 [`Composer.tsx:173–180`](../ui/src/features/chat/Composer.tsx#L173)。拖入和粘贴在事件发生时捕获；无目标会话则提示并退出，不读完后猜新 activeKey。同一批保持文件选择顺序；独立批按完成提交顺序追加，首版不引入全局串行队列。
6. `addPaths` 中 refs 也使用同一个有效目标令牌进行原子追加，虽已有 session 绑定，仍需防关闭/草稿替换后的迟到回填。目录授权仍发送原 sessionId；每个 await 后、尤其授权询问应答后先验证令牌。若目标已关闭/替换，不再发新的放行 IPC，也不把该导入改派给 B。已经获批并完成的目录权限变更不自动撤销，附件失效不会伪装成授权回滚。
7. 明确生命周期 API：保留 `setDraftImages` 的同步兼容用法，但添加具名 `replaceDraftImages`/`removeDraftImage` 或内部意图区分，整份替换负责递增 attachmentEpoch，单项删除只更新最新数组。`clearDraft` 和 `dispose` 必须失效令牌；`uiState` 恢复/保留草稿重开通过新实例代次初始化，不能复用关闭前 token。不持久化 pending FileReader 和 token，重启后无悬空读取。
8. 发送必须接入 store 的 `beginSend(sessionId)` / `completeSend(sendId, accepted)`，替换 `await send → clearDraft`。`beginSend` 在同一同步读状态内生成不可变快照，含 `sessionId/instanceId/sendId`、text/refs 的字段 revision、图片 id 集合及实际 wire payload；调用 `send(payload.text, payload.images, snapshot.sessionId)` 显式路由。`completeSend` 是一次原子更新：失败不消费；成功只在同一实例且未消费过该 sendId 时，清空 revision 仍与快照相同的 text/refs 字段，移除仍属于同一附件 epoch 的已发送图片 id，保留后来追加的图片。text/refs 在等待期间被修改则完整保留当前字段，不猜测任意编辑的字符串差分；这是可能保留已发送前缀、但绝不吞掉新文字的保守策略。若整份草稿/图片被替换，则不修改新代次内容。完成回调不得重建已关闭桶，也不得移动当前 B 的光标；仅当仍显示同实例且相关字段确实被消费时同步光标/历史浏览状态。
9. 合法的在途导入没有进入发送快照，不因受理而失效，完成后追加到原会话的剩余未发送草稿；显式关闭/清空/替换仍令其失效。若发起发送时存在在途附件，显示“图片仍在读取，将留在草稿，不会补入本条消息”的提示，避免用户以为已发送。成功消费不增加 attachmentEpoch，也不能用旧 images 数组重建已发送图片，因此不会让已消费图片复活。发送失败保持快照及期间新增内容；重复受理回调按 sendId 幂等。首版允许发送继续进行，不自动等待或补发附件。

**取舍与替代**：只把 setter 包为 `(updater) => setDraftImages(updater, capturedSessionId)` 能解决串会话和旧快照，但不能阻止关 Tab 后造桶或发送受理吞掉新内容，可作为早期小修但不满足完整 AC。整份草稿的 compare-and-clear 也能避免误清，却会因新增一张图片连已发送图片都留下；推荐字段 revision + 图片 id 的快照消费。文字修改时保留完整新字段可能包含已经发送的前缀，提示用户可继续编辑，不擅自删除用户重写的内容。只在切 Tab 时取消所有读取会丢弃用户希望留在 A 的附件；本方案允许 A 的在途读取继续写 A。全局排队读取最简单但拖慢不同会话且仍需生命周期令牌，本轮不采用。

### 兼容与边界

- 不改 Rust IPC、PendingImage wire 字段、持久化草稿结构与原地引用格式；旧 ui-state 载入时建立新的瞬态实例/代次。保留已有 text/refs/images 三项覆盖规则，包括队列无图时保留现有图片这一行为，不因重构顺手更改。
- 不能把任意 `setDraftImages` 都解释为“使旧请求失效”：单项移除若误递增，会无故取消仍在导入的其他图片。要求逐个审计 Composer、历史召回、`ws:composer-fill`、队列编辑、uiState 恢复以及测试直接 set 的调用点。
- 迟到结果的取消以逻辑丢弃为底线；FileReader 能 abort 时可回收，IPC 不支持 abort 也不得写错桶。组件临时因 AskPanel 隐藏不等于用户丢弃原草稿，不以组件卸载一概作废。
- `stale` 不显示另一个会话里的误导性成功消息；需要提示时附原会话可辨名称且只提示一次。读取失败不改已有图，MIME/单图超限拒绝单张，批内其他合法项按既有策略处理。
- 多个外部目录询问可能共用单个 `extResolve`；本轮新增/复用串行询问队列或明确“同一时间一个询问，后续导入排队”，不能让两个未决 Promise 互相覆盖。此处是附件导入正确完成的依赖，权限内容和确认粒度维持现状。
- 回滚不涉及数据迁移，可回退新 API 调用与 transient 状态；已写入合法草稿图片仍由旧版读取。若需要紧急降级，可暂时禁用并发导入并在会话切换时明确取消导入，但不得重新允许隐式 activeKey 写回。

使用受控 deferred Promise 和 mock FileReader，显式排列回调完成顺序，不依赖 sleep 赌时序；组件测试挂载真实 Composer/store，至少一个用例覆盖原生选择框前后两个 await。

## R08 MCP 配置保存只重连受影响连接

### 场景与证据

项目 A 修改一个 MCP server 的地址/参数，项目 B 和临时会话的其它 MCP 连接也全部被停止并重建；在途工具可能失败、进程状态丢失，用户看不到与本次局部编辑相称的影响范围。

- `mcp_save_config` 原子写目标文件后无条件 `disconnect_all()`，再遍历全部会话 warm，见 [mcp.rs:194–236](../src-tauri/src/host/commands/mcp.rs#L194-L236)。注释声称“其它会话不受牵连”，与实际调用不符。
- 全停实现清空每项 peer/tools、递增 generation、停止 service，且清空 `inner.sessions`，见 [manager.rs:471–500](../src-tauri/src/mcp/manager.rs#L471-L500)。全停事件 session 为空，又被 host sink 忽略，见 [mcp.rs:19–36](../src-tauri/src/host/commands/mcp.rs#L19-L36)，不能用界面没有停止事件认定连接未断。
- 反证边界：作用域可见集本身已按“项目同名覆盖全局，覆盖后再过滤 enabled”实现，见 [mcp.rs:56–76](../src-tauri/src/host/commands/mcp.rs#L56-L76)。generation 已能拒绝过期握手，见 [manager.rs:646–679](../src-tauri/src/mcp/manager.rs#L646-L679)。这些基础可复用。
- **不能只删 disconnect_all 再 warm**：`register_session` 替换 cfg 后仅给非 Ready 项建连，而 `ensure` 对 Ready 直接返回，见 [manager.rs:363–395](../src-tauri/src/mcp/manager.rs#L363-L395)、[manager.rs:571–588](../src-tauri/src/mcp/manager.rs#L571-L588)；这样会出现“新 cfg + 旧进程/旧工具”。前端保存后还多调一次 connect，见 [SettingsPage.tsx:894–920](../ui/src/features/panels/SettingsPage.tsx#L894-L920)。
- 配置还有审批“始终允许”的独立读改写入口 [config.rs:610–644](../src-tauri/src/mcp/config.rs#L610-L644)，由 [batch.rs:498–509](../src-tauri/src/tools/batch.rs#L498-L509) 调用；仅串行化设置页保存不能防止两条写链互相覆盖。审批在 [batch.rs:468–486](../src-tauri/src/tools/batch.rs#L468-L486) 读取目标后 await，批准后再按当前 scope 写允许并调用；[manager.rs:941–977](../src-tauri/src/mcp/manager.rs#L941-L977) 又用当时工具集合按函数名重新定位，存在批准旧目标后同名配置/作用域已变化的窗口。
- 当前调用确实不自动重连重放，见 [manager.rs:934–1002](../src-tauri/src/mcp/manager.rs#L934-L1002)。本次没有建立 MCP 连接或测量真实在途调用失败，只能确认断连范围与风险，不能声称每个调用必然被中断。

### 目标与设计

目标：格式化/等价保存不重启任何连接；有效配置没变化的 PoolKey 保留同一连接、pid、generation、引用集合与在途调用；只有新增、移除或有效配置变化的 key 更新，所有引用它的会话得到一致状态。非目标：MCP 写调用自动重试、无缝迁移有状态 server、承诺被修改 server 的在途调用永不中断、引入所有旧 MCP IPC 适配。

推荐：在 `mcp` 层增加“配置提交 + 可见集差量计划 + 管理器 reconcile”的明确职责，host 只解析入参与转调。

1. 配置解析提取纯函数 `parse_scope_text(scope, text)`，由现有磁盘 loader、保存验证与 R11 草稿测试共用；移除保存时固定名字 `mcp.validate.json` 的临时验证文件。当前配置已 `PartialEq` 且保留 extra，见 [config.rs:158–199](../src-tauri/src/mcp/config.rs#L158-L199)。用解析后的配置做语义比较，JSON 空白/键顺序不触发重启；未知扩展字段变化采取保守“仅此 key 重启”。设置页编辑第一版可保守按条目重启；审批产生的单字段 always_allow 补丁需走下述受约束的政策热更新，不能为了记住本次批准而自行使调用票据失效。
2. 引入配置提交协调锁（全局一把短锁即可，避免同一会话同时受全局/项目提交影响）：校验 → 读取目标旧文档/取得版本 → 计算 affected scope → 原子写新文件 → 在 manager 锁内提交 desired revision/差量计划；网络连接与 service.cancel 必须在锁外。保存冲突用已读内容版本做乐观检查，版本不符返回冲突并保留草稿，避免两个编辑器互相覆盖。`set_always_allow` 也必须进入同一协调器：以字段补丁、expected source identity、expected target generation/config revision 读取最新文档并提交，仅改已批准目标的允许字段，保留其它条目/未知字段，随后 reconcile 该 key 的运行时政策；不得继续调用独立无锁的原文读改写，也不能在批准返回后按 server 名重新查询作用域。无关文档字段变化可重读后合并补丁，目标本身变化则拒绝，绝不把旧“始终允许”写入新 scope/新端点。
3. 为受影响会话计算完整新可见集，不按“server 名等于修改名”草率定位。项目保存仅影响实际读取该项目配置文件的 runtime；全局保存影响所有会话，但某项目覆盖同名全局项时，其有效项目 key 不变。删除项目覆盖项可能暴露全局同名项；项目 disabled 覆盖仍应遮蔽全局，不能错误回落连接。
4. manager 在一次短锁内完成引用集合差分：未变 key 不碰；移除 key 撤掉对应会话引用，引用归零才回收；changed key 替换 desired cfg、推进 generation、作废旧 pending handshake，撤下旧工具并针对该 key 重建；added key 先登记引用再建连。共享 global key 只建连一次，按 key 的 generation/connecting single-flight 去重，不能每个受影响会话各 spawn 一个握手。
5. 保存成功的语义为“已写文件并接纳应用计划”，返回 `saved / issues / apply_revision / affected_servers`；Ready/Error 仍异步通过现有 `mcp:status` 与 snapshot 收敛。事件发给此 key 的受影响会话，含可选 revision/generation 以拒绝迟到状态；不新增/改名现有事件键。前端删掉保存后的无条件 mcpConnect，只刷新 snapshot，显示实际应用中/失败状态，不把 saved 等同连接成功。
6. 会话关闭/打开、手动 disconnect/reconnect 也必须使用同一 desired revision。关掉会话后迟到 warm 不得重新登记引用；旧保存计划/旧握手不得覆写新计划。原 `disconnect_all` 保留用于应用退出等明确全停场景，不参与普通配置保存。
7. **工具快照、审批与 dispatch 必须贯穿同一调用票据**：在构建每次 LLM 请求的工具定义时，私有映射保存 `CallBinding { function, original_tool, PoolKey, source_identity, connection_generation, config_revision, policy_revision, tool_schema_revision }`，随本 step 的模型回包流入 batch；不向模型公开内部票据。审批展示与策略判定读取该绑定，不按当前同名项重猜。批准后 manager 在同一短锁中验证会话仍可见、目标来源/代数/工具映射及 schema/政策版本未变，并取得对应 peer 才允许发出请求；不匹配返回明确“配置已变，请重新发起调用”，禁止自动转发给新 endpoint，也不套用旧批准。没有人工审批的 read_only/always_allow 调用同样校验。专用 always_allow 补丁只有在原绑定所有其它目标字段及 schema 完全一致时才可热更新政策；它只提升独立 policy_revision，不改变 transport/connection generation，也不重建 peer。本次一次批准仍绑定原目标和 schema，协调器返回仅政策版本更新的已验证票据；不允许刷新目标代数来掩盖 endpoint/scope/工具变化，后续再发生配置变化仍须拒绝。tools/list_changed 刷新若改变工具映射/schema，也推进 tool_schema_revision，使旧请求绑定不能悄悄指向新定义。目标绑定失效检查发生在真正 dispatch 之前，不能只在进入审批前查一次。

取舍：按作用域全停比现状好，但仍会打断同项目未修改 server，且全局作用域会波及大量共享连接；不能满足“只重连受影响 key”。为受影响连接等待在途调用排空是可选后续优化，不能为了本轮引入无界等待。第一版允许受影响连接取消在途调用，必须显示失败原因且绝不自动重放。

### 兼容与边界

- 当前 PoolKey 只有 scope/project_id/name；runtime 的 project_dir 是会话快照。若同 project_id 的活跃会话可能指向迁址前后两份配置，单凭 pid 不能识别配置来源。本轮设计应给内部 key/来源身份补规范化的配置路径身份（不传给模型、不暴露密钥、不改变 mcp.json）；至少要测试这一冲突，不能以 pid 相同推定配置相同。公开 UI 的 scope/name 仍按当前会话解析。
- 配置写失败不触动池；写成功但连接失败保留新配置并报该 server Error，不偷偷还原旧安全策略。对已删除/禁用条目立刻撤出新工具调用入口；已发出的外部副作用不能撤回，既不重放也不把取消称为“未生效”。
- 仍保持 server 配置未知字段、工具过滤、原作用域 always_allow 的持久化与项目 disabled 覆盖契约。没有用户可见配置 schema 迁移；IPC 可增字段且同时更新 TS，当前前后端同包发布，不恢复已移除旧接口。
- 断连、握手失败、取消与初始化超时都必须回收进程树；不受影响 pid 不变是硬验收项。日志只记 scope/key/revision/变化分类，不打印 env/headers 原值或完整配置 diff。

## R09 一次任务执行后保留实体与结果

### 场景与证据

用户安排 once 任务，任务触发后列表消失；运行结束时的摘要可能短暂随事件显示，却无法在任务历史中回看，重启还可能删除原任务文件。失败与 skipped 同样没有稳定记录，用户无法判断任务是否真的执行。

- `tick` 把 once 快照加入 due 后直接 `tasks.remove`，见 [scheduler.rs:373–383](../src-tauri/src/core/scheduler.rs#L373-L383)。`record_run` 查不到 id 则静默返回，见 [scheduler.rs:256–267](../src-tauri/src/core/scheduler.rs#L256-L267)。正常/失败收尾和项目无效 skipped 都调用它，见 [scheduler.rs:497–528](../src-tauri/src/core/scheduler.rs#L497-L528)、[scheduler.rs:579–611](../src-tauri/src/core/scheduler.rs#L579-L611)。
- 恢复路径还会删除 next_run 已过去的 once 文件，见 [scheduler.rs:316–325](../src-tauri/src/core/scheduler.rs#L316-L325)。这条路径目前又被 R05 的错目录扫描部分遮蔽；修 R05 后若不联修 R09，会使真实项目的过期 once 开始被这段删除逻辑命中。
- 反证边界：wait_targets 与任务实体解耦，仍可接收完成态，项目任务文本日志也可能存在；不能说所有执行信息物理丢失。但任务列表/runs 的回看契约确实断裂。UI 收到 done 后会重新拉后端列表，见 [tasks.ts:71–91](../ui/src/stores/tasks.ts#L71-L91)，不能靠事件补一条本地假任务修复。
- 当前 UI 已按“once 的 next_run=None 表示不再触发”设计，见 [TasksPage.tsx:161–170](../ui/src/features/panels/TasksPage.tsx#L161-L170)。现有后端测试反而明确断言 once 被移除，见 [scheduler.rs:914–951](../src-tauri/src/core/scheduler.rs#L914-L951)，需改正该断言而非保留错误行为。
- 以上均静态核实；本轮没有验证真实运行、磁盘崩溃恢复或结果 GUI。

### 目标与设计

目标：一次调度机会被消费后保留任务、状态和最多 20 条历史；无论 ok/error/skipped 都可回看；重复 tick 不重复自动执行；重启不猜测“已经成功”，不删除唯一任务文件。非目标：无限任务转录、执行外部操作 exactly-once、自动重放崩溃前的写操作、任务管理功能大改版。

推荐与 R06 共用任务实体/执行实例分离：

1. 认领成功时保留 `ScheduledTask`，once 的 next_run 置 None；enabled 保留为用户启停偏好，不能用它混淆“已执行”“用户暂停”。不存在下一次触发不等于执行成功，完成结果仍取 runs/last_status。
2. 为所有任务新增可选 `active_run { run_id, source, scheduled_for, started_at }`，serde default；`TaskRun` 增可选 run_id，用于 finish 幂等。认领事务先持久化 active_run 与 next_run，再允许开始执行。内存 execution snapshot 保存实际执行的指令/计划；active_run 不需复制敏感全文。手动运行不改 next_run。
3. `finish_run` 单次事务同时更新 last_status/last_summary、按 run_id 去重插入 runs、截到 20 条、清 active_run，并落盘。当前“先单独改 last，再另调 record_run”的两段写改为一个入口。任何终态均保留 once 实体；用户已显式删除的任务不能被 finish 重新创建。
4. 新进程发现 active_run 非空，表示曾认领但没有可靠收尾记录，记录 `error`、摘要“上次执行中断，结果未确认”，清 active_run，**不自动重试**；一次任务保持 next_run=None，循环任务保留已推进的 next_run。恢复提交也按 run_id 去重，连续重启不得追加多条同一中断记录；写失败保留诊断和不重放状态，不能假称收尾已保存。
5. 未认领但停机期间过期的 once 需明确产品策略。推荐保守默认：保留实体、清 next_run，记一条 `skipped`“应用离线时已错过计划时间”，不突然补跑旧 FullAccess 指令。提供现有“立即运行”或改为未来 once 的重新安排路径。处于 paused 的过期 once 不生成运行记录，保持暂停与原信息；用户启用时继续要求改成未来时间。该选择沿用“不自动恢复过去 once 的执行”的方向，同时消除删数据，不声称当前代码已具备此区分。
6. `list_scheduled_tasks` 同时返回 active_run，前端 `stores/tasks.ts` 以当前列表和 run_id 对账 running 标记，scheduled:fired/done 增可选 run_id但事件名不变；迟到 done 不得清掉新手动 run。列表 load 增 generation/revision 防旧响应盖掉编辑/删除；非法非数组返回应保留旧列表并报错，不能当前实现那样置空，见 [tasks.ts:50–60](../ui/src/stores/tasks.ts#L50-L60)。
7. UI 已消费 once 仍可展开历史、编辑、删除、手动运行；改指令/名称不自动重新安排，改为未来 schedule 才生成 next_run。已消费 once 的开关不要呈现“打开即可再次执行”的错觉，需提示“修改时间以重新安排”；运行态、暂停、无后续触发分别展示，中英文文案同步。

取舍：单纯把 `tasks.remove` 改为 next_run=None 可修正常收尾的主体问题，却不能解释“认领后进程退出”的状态，也不能防止收尾重入/迟到事件。本轮推荐最小 active_run/run_id；完整 append-only 执行日志与任务审计数据库留后续，不借此改造主会话历史。

### 兼容与边界

- 仅新增可选字段，读取当前任务文件无需旧 schema 转换；不再删除过期 once 文件。不从日志猜补历史，不创建“历史迁移器”。当前格式无 active_run 的 next_run=None once 只展示“无后续触发/已有记录”，不能伪造成功。
- 崩溃窗口在 durable claim 之后、外部副作用之前/之后无法仅凭本地标记区分，保证是“不会自动盲目重放，结果未确认可见”，不是 exactly-once。完成落盘失败时保留内存结果与未保存标志，可有界重试同 run_id；用户删除/项目删除后停止重试，避免数据复活。
- 执行期间改 schedule 为未来值，finish 只合并本 run 结果、清匹配 active_run，不把新 next_run 清空。旧 once 手动运行不消耗新设 future schedule。pause 不会抹掉真实在途 run 的记录；“暂停不记历史”仅指未获执行资格的定时机会。
- 运行日志仍在项目 logs，任务实体删除按现有用户意图处理；本轮不承诺完整转录可回看。无项目任务只有进程内记录，保持现有边界。
- 回滚前停止调度并备份任务文件；旧代码忽略新增字段可能再次删除 once，并无法识别未确认执行，故**不能把旧二进制重新开启调度作为无风险回滚**。安全回退应使用暂停调度模式或前向修复，保留文件与诊断；不自动复制/降级 schema。

## R10 即时子代理模型设置与页级草稿隔离

### 场景与证据

同一次打开设置页，用户先把 `backend-dev` 改用模型 B，随后调整日志/网络等普通字段并点顶部保存。第一次选择已经即时落盘；第二次却可能把打开页面时的旧 `subagent_models` 整体写回。损害是用户以为选好的角色模型丢失，后续子代理可能使用非预期的模型、费用和能力配置。连续快速改两个角色还可能互相覆盖各自的旧完整快照。

### 目标与设计

**推荐保留即时生效语义，改为后端字段所有权 + 专用 patch + 版本化提交。** 角色选择无需点击顶部保存；取消普通草稿不撤销已成功保存的角色选择；普通保存不得读取或覆盖陈旧角色图。非目标是统一所有偏好为自动保存、即时改变已运行子代理的 spawn 模型快照，或扩大角色委派权限。

1. 新增 `set_subagent_model { role, model_id: string|null, expected_role_version, operation_id }`，只允许当前 `DELEGABLE_ROLES`；沿既有角色归一入口校验，非空 id 必须在最新已提交 providers 中存在。未知角色/model 返回结构化错误，不按客户端全图覆盖。核心执行单角色 patch，命令注册/IPC wrapper/类型同时更新，返回与 R01 同形的脱敏权威快照及版本。
2. 明确所有权：`subagent_models` 仅专用命令维护；`ui.font_sans/font_mono` 仍由字体命令维护；主草稿只拥有其余列明的页级配置字段。现阶段保留全量页提交也可以，但后端在同一提交锁内强制用最新独立字段覆盖请求值，并逐步将输入改成页级可写 DTO。不能仅靠 UI 删掉某字段就认为后端安全。
3. 与 R01 共用配置串行器，覆盖 [`AgentCore.cfg`](../src-tauri/src/core/agent/runtime.rs#L519-L524) 的持久化入口。特别纳入 [`toggle_skill`](../src-tauri/src/host/commands/skills.rs#L74-L89) 和 [`命令“始终允许”白名单持久化`](../src-tauri/src/tools/command/tool.rs#L774-L784)，否则任一 `snapshot.save()` 仍能把新角色/凭据引用盖回。白名单采用最新配置上的去重追加 patch，变更计入 page_version；保存失败只影响未来的持久授权，不改变本次明确批准的命令结果；运行时 [`ensure_subagent_models`](../src-tauri/src/tools/subagent.rs#L475-L487) 不再绕过版本/提交真值随意改全局配置，可在构造时补缺省或让读取把缺省视为 null。
4. 版本分“全局快照版本”和“写者拥有的字段域版本”：返回 `version={boot_id, sequence}`、`page_version`、每角色 `role_version`。运行期间每次提交递增全局 sequence；页拥有字段变化才增 page_version，某角色变化才增该角色版本。打开页面保存其 page_version；角色即时保存不会制造无关页面冲突。若另一个写者修改了页级字段，则旧 draft 提交报 `ConfigConflict`，保留草稿并提示重新核对，不能自动重放整个旧配置。重启后 boot_id 改变，旧客户端版本一律冲突；无需为这些会话并发 token 增加历史 schema 迁移。
5. 前端 store 对新快照按 `{boot_id, sequence}` 对账，晚到的旧响应不能覆盖新状态；只有一次明确成功的配置加载才能建立新的 boot_id，未知启动代的迟到保存响应不可自行切换 store 代际。每个角色单独 `pending/error`，同角色在途时禁用或合并为最后一个尚未发出的意图，不允许并行提交两个旧版本。同一角色冲突保持后端值并要求用户确认新选择，不同角色 patch 可以顺序合并不相互抹除。
6. UI 成功前不把未落盘值冒充已保存；失败只恢复该角色展示并保留可重试的选择，不重置整个 SettingsPage 草稿。顶部提交后用返回快照建立新的已保存基线；如果用户在保存等待中继续编辑普通字段，按提交时的 draft generation 仅确认本次已提交内容，保留后续编辑为 dirty，不能 `setDraft(response.config)` 一把清空。
7. 注册表将 `subagentModels` 明确列入即时项；需要读取该 UI 别名时显式映射 `subagent_models`，不依赖路径 drill 的偶然 undefined。职责测试要求每个可编辑字段明确属于“主草稿/即时 patch/独立文件”之一，且 IPC 写者与分类对应。角色选项继续读已提交 providers；新加但还未保存的模型不作为可即时选择项，可在附近说明“先保存模型再选择”。

**替代与取舍：** 把 `SubagentModelsPanel` 改成受控 draft、完全随顶部保存，能较快消除双写者，但改变当前即时行为，必须同步脏点、取消、导航拦截和文案；若产品愿意统一保存可单独选它。只在保存前从 store 拷贝角色图或监听 store 刷新整份 draft 都不推荐：前者留后端/并发窗口，后者会丢用户尚未保存的其它输入。

### 兼容与边界

- 持久化仍为 `subagent_models: role -> model_id|null`，缺省空图/缺键等于继承；无必要数据迁移，不重新接纳历史 schema。IPC 为同一应用发行的双端同步变化；旧全量调用仍经过后端保护，不能绕过所有权。
- 模型被删除时在同一次页提交内把受影响的当前角色引用归一为 null，并在结果中说明受影响角色；这是模型删除的可见结果，不是恢复旧草稿。并发“选 B/删 B”：先选后删则最终继承且有提示；先删后选则角色 patch 返回模型不存在，刷新选项。
- 两个不同角色可各自保存成功；相同角色以 expected_role_version 检出冲突。普通页保存与字体、角色 patch 无损合并；技能独立变化或命令审批白名单追加属页级域，会使旧整份页草稿冲突而不是静默覆盖；页面里删除/清空白名单同样要按该版本冲突检查，不能撤销刚追加的持久授权而无提示。
- 角色选择保存只影响后续 spawn 的模型决议；现有 [子代理运行契约](./subagents.md) 的模型/思考力度 spawn 快照不改。顶部取消/放弃只取消普通草稿，已经成功的即时角色值重开仍保留；角色保存失败时不能显示已生效。
- 页保存不因角色 patch 触发会话清理、HTTP client 重建或 KeyPool 清零；协调器按真实字段变化选择后处理，避免一次角色选择携带完整配置和无关副作用。已有当前明文凭据则遵守 R01 的安全写入限制，明确报错，不借专用 patch 重新写明文。
- 可回滚前端选择体验，但后端字段保护、单一提交器和权威快照返回必须作为一组保留，禁止只回滚其中一层恢复旧全量覆盖。

## R11 MCP 编辑框测试使用当前草稿

### 场景与证据

用户改了 command、args、env、URL 或 headers，点击“测试”后却测到磁盘旧配置；新建/重命名条目还可能报“配置里没有此 server”。这会给出错误的通过结论，用户随后保存才发现真正配置不可用。

- 编辑状态存于 `mcpDoc/mcpEntries`，字段修改只更新草稿，见 [SettingsPage.tsx:306–324](../ui/src/features/panels/SettingsPage.tsx#L306-L324)、[SettingsPage.tsx:927–975](../ui/src/features/panels/SettingsPage.tsx#L927-L975)。按钮只传 `e.name.trim()`，见 [SettingsPage.tsx:1786](../ui/src/features/panels/SettingsPage.tsx#L1786)。
- `testMcpServer` 仅传 scope/name/sessionId，见 [SettingsPage.tsx:1085–1100](../ui/src/features/panels/SettingsPage.tsx#L1085-L1100)、[client.ts:181–182](../ui/src/ipc/client.ts#L181-L182)。后端重新 load_scope 并按 name 查磁盘配置，见 [mcp.rs:307–330](../src-tauri/src/host/commands/mcp.rs#L307-L330)。
- 反证边界：测试确为临时连接，`test_connection` 不并入池，完成后回收，见 [manager.rs:1033–1045](../src-tauri/src/mcp/manager.rs#L1033-L1045)。现有 UI 测试只断言 scope/name 与不触发 connect，见 [settings.mcp.test.tsx:622–637](../ui/src/__tests__/settings.mcp.test.tsx#L622-L637)，没有断言草稿字段被送到后端。当前 [设置指南](./settings-guide.md#mcp-页与编辑器) 已明示测试已保存配置，因此本项是有意改进该现行边界，文档也须同步，不能只改测试名。
- 本次未启动 MCP、未传输用户凭据、未 GUI 复现；静态链路足以确认输入源错误与缺失覆盖。

### 目标与设计

目标：编辑器“测试”针对点击瞬间的当前条目草稿，新建/重命名无需先保存；结果明确绑定这份草稿，之后修改字段就失效；测试不写 mcp.json、不连正式池、不影响保存基线。非目标：测试自动保存、自动安装 npx 包、调用 server 的业务工具验证副作用、验证所有 MCP 功能或连接后长期可用。

推荐方案：

1. 在 `ui/utils/mcpConfig.ts` 提取 `serializeMcpServer(draft)`，复用现有整文档序列化中的条目逻辑，见 [mcpConfig.ts:191–236](../ui/src/utils/mcpConfig.ts#L191-L236)。保存与测试共享字段转换，完整保留显式 transport、args 数组、env/headers 多行值、cwd、timeout、tools、read_only/always_allow 与未知 extra；测试不另造一套不完整的对象映射。空名称、重复名称、键值行重复/非法 timeout 等在送出前明确报错，不以序列化丢字段模拟有效输入。
2. 保持 `mcp_test` 命令名，改为接收当前 `name + config: Value`（scope/sessionId 仅用于合法上下文/显示归属，可按现有约束保留）。config 必传；后端反序列化为 `McpServerConfig`，调用与保存相同的纯校验逻辑后直接 `test_connection`，**不读取同名磁盘条目，不在草稿非法时回退旧配置**。当前所有调用方同版本更新，不为已移除旧 IPC/schema 新增桥接。若以后确实要“测试已保存配置”，另做清楚标注的用户动作，不让同一按钮隐式切输入源。
3. 后端 host 只校验上下文/转调测试服务；解析与校验放 mcp/config，probe 生命周期放 manager。R08 提取的纯 parser/validator可共用，测试绝不为验证写临时 JSON 或把含密钥的草稿落盘。测试只 initialize/tools/list，成功只能称“当前草稿握手成功并发现 N 个工具”。
4. UI 在点击瞬间捕获不可变 config、editorSessionId、scope、条目本地身份、draftRevision、requestId。结果状态不是单纯 `Record<name,...>`：重命名/同名作用域/关闭重开均不能复用旧成功。任何字段修改使旧结果变为“草稿已变更，需重新测试”或清除；响应仅在 editor generation、draft revision、requestId 全匹配时接纳。
5. 单条目测试在途按钮 loading/禁重复；关闭编辑器/放弃/切会话取消接纳结果并发后端取消（若增加取消 token/测试 id）；即使 UI 已关闭，后端也必须有初始化+tools/list 的统一上限与回收。现有 initialize 和 tools/list 分别使用 30 秒上限，并非整个 probe 合计 30 秒，见 [manager.rs:773–792](../src-tauri/src/mcp/manager.rs#L773-L792)。推荐保留这两个阶段上限并设置明确的总体预算（例如 60 秒，清理另有有限预算）；不能用业务调用 timeout_ms 冒充初始化上限。以 RAII 确保成功、失败、取消、超时、panic 后子进程回收。
6. 按现有安全说明提示“测试会临时启动所填命令或连接所填地址”，保留用户显式点击才执行的边界。日志/错误不能输出 env/headers 值、原始 config 或 Authorization；远端/启动器错误可能含敏感 URL，要对展示与 tracing 做结构化脱敏。不要把“未保存”写成“无副作用”，因为 stdio 启动本身可以有副作用。

取舍：提示“先保存再测试”实现最省，但需要把尚未验证配置应用到真实连接池，不满足编辑器期望；将磁盘配置暂存替换再恢复会有并发、泄密与崩溃窗口，禁止采用。直接传完整当前条目草稿是范围最小且可验证的方案。

### 兼容与边界

- mcp.json 格式不变，不做迁移；纯 serializer 必须守住现有未知字段和多行值往返。IPC 入参是当前版本接口调整，Rust/TS/测试在同一提交更新，新增结果字段按可选处理。
- 新条目与重命名条目可测试；重名应前置阻断，不能让整文档对象后写覆盖前写后再测错条目。disabled 草稿允许显式临时测试，但不修改 enabled、不登记正式引用。
- project/global 只决定编辑归属，测试当前选中的原始条目，不测试合并后另一个作用域的同名 server；UI 清楚标注来源。全局无活动会话也可测试；项目上下文在测试前已失效则报错，不偷偷切全局。
- 保存后新基线可以与刚测草稿一致，但测试成功不代表正式连接成功；网络、环境/凭据有效期可变，必须继续观察 R08 的正式状态。迟到成功不覆盖用户新字段，不关闭弹框，不移动保存基线。
- 安全回滚是前后端共同回退接口并禁用/明确标注草稿测试，不能静默重新读取磁盘却沿用“当前草稿测试”文案。若测试取消实现暂缓，必须仍有确定超时和完整回收，且披露取消编辑不等于立即杀 probe。

### 测试与验收

| 测试面 | AC |
|---|---|
| 磁盘有效 A，草稿无效 B | 后端使用 B 返回失败，绝不因 A 可用报成功；文件字节/mtime 不变 |
| 磁盘无条目，新建/重命名草稿 | 使用新名称+完整 config，正常探测，不报磁盘不存在 |

每项需在对应修复 PR 写明：基线及最终 commit、实现了哪些设计、哪些建议被替换及理由、测试命令/工作目录/平台/退出码、人工验收者和结果、仍未覆盖的边界。下列条件全部满足才可标记关闭：

- 本节与各项矩阵中的核心失败用例已先证明能捕获旧行为；生产调用点的回归已通过。无法在旧版本直接运行的新接口用例，须另给旧调用链最小复现或约束断言。
- 磁盘、内存、UI 和事件携带的 resource ID/revision 一致；错误注入未出现静默覆盖、虚假成功、迟到复活或无关资源断连。
- 新格式的默认值、读取、写入失败、退出后重启以及受控回退均有测试。升级前后样本使用合成数据，真实密钥、私有文档与本机绝对路径不提交。
- 用户可见状态和错误完成中英 i18n；新可选字段同步两端；事件契约只守键名不能代替 payload 测试。
- 独立审查覆盖正确性、安全、性能、可维护性、可读性、测试和最佳实践；严重发现全部关闭，一般风险明确归属与计划。

### 自动门禁

未来修复在开 PR 或发布前，从仓库根执行 `pnpm prepr`，与 [完整门禁](./testing.md#开-pr-前的完整门禁) 保持同源。它包含锁定依赖安装、Rust fmt/clippy/test、UI lint/test/build 和 Node 脚本测试。硬步骤失败即停；clippy 仍按现行规则作为软步骤单独报告，不能用总退出码掩盖新增 warning。

开发中可先执行针对性测试，但不替代完整门禁：

| 改动范围 | 最低针对性回归 |
|---|---|
| R01/R02/R10 | keyring 假后端及 config 提交测试；`settings.page`、`settings.registry` 与新增多写者/密钥池测试；脱敏回执契约 |
| R03/R04 | Office 编辑/写入/还原故障注入，claim 和路径写锁回归，普通文本工具与任务/子代理隔离回归 |
| R05/R06/R09 | 正式项目注册布局 roundtrip、scheduler 虚拟时钟/锁竞争、任务列表与终态重启恢复、IPC 失败回执 |
| R07 | Composer 完整挂载、附件导入 deferred promise、run store 关闭/清空/发送/切换/取消竞态 |
| R08/R11 | MCP manager 配置差异、连接世代、调用票据与回收、模拟 server in-flight 行为、草稿测试弹框及迟到结果 |

具体执行以仓库实际新增测试文件为准；这些测试名称或类别是未来实施要求，不表示当前已经存在或执行。后端命令在 `src-tauri/` 执行 `cargo test --workspace`；UI 从根执行 `pnpm --dir ui test`、`pnpm --dir ui run lint`、`pnpm --dir ui build`。

### 平台与人工门禁

按仓库约定提供分步人工清单，不做 GUI 自动点验。macOS、Windows、Linux 的 CI 结果分别记录；其中系统钥匙串、文件占用/替换、WebView 文件导入、MCP stdio 进程回收还需真实平台验收，不能从单平台结果外推。

1. **凭据**：系统钥匙串可用/拒绝/锁定各测一轮保存和重启；观察错误与持久化结果，检测测试假 key 是否出现在配置/临时文件/日志。已有安全引用仍能读取，且新失败不破坏旧池。
2. **Office**：打开有图表等非目标内容的合成文件；拒绝备份、模拟目标被占用、并发修改与取消；逐步确认原始字节、备份、目标结果、UI 回执与还原后的内容一致。
3. **调度**：用两个已注册项目建 every/once 任务，重启；一个长任务占锁时暂停、删除和修改另一个 pending；观察实际执行次数和持久化终态，不只看 toast。
4. **附件与设置**：A/B 两个 Tab 切换导入，导入未完时发送/清空/关闭；设置页保持旧草稿时改子代理模型，再点保存、取消、重开；确认资源归属及独立字段均未丢失。
5. **MCP**：A/B 项目与临时会话保持连接和在途请求；保存 A 配置后 B 不受影响；编辑草稿但不保存时测试，其结果对应当前草稿；取消/失败后临时测试进程和连接已回收。

### 上线与回退原则

先在合成数据及内部测试配置验证，再按功能分批发布。功能开关只能关闭**新增写入/调度能力**或退回受控错误，不能恢复已知不安全的明文预写、无备份覆盖或旧 once 删除路径。回退之前暂停相关执行，备份受影响的当前数据与非秘密版本信息，按章节指定的兼容边界验证；不把“二进制能启动”当作数据可回滚证明。

如凭据引用或任务生命周期字段已被新版本写入，而旧版本会忽略、误解或覆盖它们，则阻止直接降级，保留最后一个能理解新格式的修补版本；必要时设计显式、可验证的向前修复。不能靠复制旧配置或删除新字段伪造成功回退。

## 决策清单

实施前由维护者确认以下产品语义，其余按各节推荐方案推进：

- R01：系统钥匙串不可用时，是否另设明确的临时/明文模式。默认推荐安全失败并保留旧有效配置；若允许降级，必须单独取得用户明确选择并准确显示风险。
- R03/R04：备份保留额度、过期清理与外部编辑冲突呈现；主会话/子代理/任务的认领粒度采用各节推荐的统一规则。
- R06/R09：暂停、删除与已开始运行的边界；过期 once 的默认处置；人工“重跑一次”是否保留同一任务及独立 run 记录。默认不自动补跑具有副作用的一次任务。
- R08：配置变更是否允许等在途调用自然结束、最大等待和显式强制取消入口；默认不为变更重放非幂等调用。
- R10：即时模型配置保持立即生效，页级取消只撤销页级草稿；主设置并发冲突是否提供字段级重应用 UI。最低要求必须可感知冲突而非静默覆盖。

所有决定及实际接口以对应修复 PR 为准。方案更新不等于授权实施修复、创建修复 PR、合并或发布。
