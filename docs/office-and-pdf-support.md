# Office 与 PDF 文件支持

> 批次日期：2026-09-21 ｜ 分支：`feat/office-pdf-support`（基线 `main` @ `9d836e5`）
> 需求与方案产物：`.codewave/tasks/20260921-013928-office-pdf-support/`（不进版本控制）

## 1. 这个批次解决什么问题

在这之前，应用只能读文本类文件与图片。用户手上的信息大量在表格、文档和 PDF 里，要交给模型只能自己复制粘贴、截图，或先转成文本——转换会丢格式、丢公式，改完还得手工搬回去。更关键的是：**模型改不了用户手上那个真实文件**。

这一批把三类文件接进工具链：读它们的内容、生成新的、并**保真地**修改已有的。

## 2. 支持范围

| 文件类型 | 读 | 生成 | 保真修改 | 界面预览 |
|---|---|---|---|---|
| `.xlsx` / `.xlsm` | 支持 | 支持 | 支持（单元格级） | 支持（表格 + 行窗口化） |
| `.docx` | 支持 | 支持 | 支持（文字级） | 支持（标题层级 + 表格） |
| `.pdf` | 支持（文字层） | 不支持 | 不支持 | 支持（网页阅读器） |
| `.csv` / `.tsv` | 已支持（走文本通道） | 已支持 | 已支持 | 支持（表格） |
| `.md` / `.txt` | 已支持 | 已支持 | 已支持 | 已支持 |
| 扫描件 PDF | 明确告知原因，不猜内容 | — | — | 支持 |
| `.xls` / `.doc` | 不支持，提示另存为新格式 | 不支持 | 不支持 | 不支持 |
| `.pptx` / `.ods` / `.rtf` | 不支持 | 不支持 | 不支持 | 不支持 |

**不做的事**：带密码的文件、PDF 正文修改、图片文字识别（OCR）、生成图表、PowerPoint、把新格式转回旧格式、结构化编辑（增删行列、增删段落表格）。

## 3. 三个新工具

| 工具 | 职责 | 分级 |
|---|---|---|
| `read_document` | 读表格 / 文档 / PDF；表格先给结构摘要再按区域取数 | ReadOnly（免审批） |
| `write_document` | 生成新的表格 / 文档 | FileWrite |
| `edit_document` | 保真修改已有的表格 / 文档 | FileWrite |

三者内部按扩展名分派。**没有把它们塞进 `read`**：`read` 只处理文本与图片，而这三类文件需要结构摘要、分页、崩溃隔离，塞进去会让一个工具的职责说不清。作为补偿，`read` 现在会**拒收二进制文档**并点名该用哪个工具——在此之前，模型读 `.xlsx` 会拿到一堆替换符乱码，然后据此编造结论。

### 读取的两条硬规则

1. **表格先给摘要，再按区域取数**。一张几十万行的表整份返回会直接灌爆上下文：不带 `sheet` 时只返回工作表名、行列数、表头与前几行；带 `sheet` + `range` 才取具体区域，单次上限 200 行 / 64 列 / 20000 格。
2. **PDF 超过 10 页必须显式指定页码**，单次最多 20 页。规则的理由是「一次拉太多既灌上下文又拖慢响应」，所以宁可要求调用方说清楚要哪几页。

### 保真修改为什么这么实现

**路线：把文件当压缩包解开 → 只替换目标内部文件 → 其余条目原样搬运 → 重打包。**

绝不「读成内存模型再整份重新序列化」。重建路线会丢掉实现没覆盖到的内容——图表、数据透视表、迷你图、切片器会凭空消失。这是格式决定的，不是实现好坏的差异：`.xlsx` / `.docx` 是压缩包里的 XML 集合，其中大多数成员本工具根本不解析，只要不碰它们，它们就还在。

具体做法：

- **单元格改写走纯文本层**（`sheet_edit.rs`）：在 `<c>` 上做定位改写，写内联字符串而**不动共享字符串表**——改共享字符串表会影响所有引用同一索引的单元格。
- **Word 文字替换跨片段回填**（`edit_word.rs`）：Word 会把一句话拆成多个 `<w:t>` 片段（拼写检查、批注锚点、修订都会造成拆分），所以按文字区间回填而不是按节点替换；不增删非文字节点，加粗与批注锚点都保留。默认只替换唯一命中，命中多处报错——改错地方比不改更糟。
- **改前持久备份**（`backup.rs`）：同一文件保留最近 5 份，供一键回退（`tools/edit/tool.rs` 的备份是「成功即删」，那条路不可复用）。
- **审批卡片展示旧值 → 新值**，一次列出全部改动。

## 4. 保真验证（怎么知道它真的没丢东西）

1. **逐字节比对**：`tools/document/faithful_spike.rs` 对 11 份真实样本（多图表 / 数据透视表 / 条件格式 / 批注 / 75 个内部文件 / 第三方产物）改动一个单元格，然后解开压缩包逐条比对——除目标条目外全部字节相同。
2. **用户用真 Excel 打开确认**：改动后的文件在真实 Excel 里打开**不弹修复提示**，图表与数据透视表都在。结论已记录在 PR 描述里（这是本批次最重要的一条验证：字节相同不等于 Excel 认）。
3. 性能实测：1.2MB 文件（内部 8.9MB）读 8ms、改 5ms、打包 78ms。

## 5. 四个文件入口

进来的文件**原地引用，不复制副本**：对话里出现的是一行 `@路径`，模型需要时自己用 `read` / `read_document` 去读。这条路的好处是大文件不占上下文，也不产生副本与原件不一致的问题。

| 入口 | 行为 |
|---|---|
| `@` 引用 | 既有能力，后端能读到就行（本批无需改动） |
| 附件按钮 | 走**原生文件选择框**（`select_document_files`），任意文件；图片读成 base64 进待发附件（模型看的是图，必须上 wire），其余插入 `@路径` |
| 拖入窗口 | 走 Tauri 事件通道（`ui/src/ipc/dragdrop.ts`）；窗口开启系统拖放后网页层的 `ondrop` 不再触发，而且网页层拿到的是 `File` 对象、没有真实路径 |
| 项目目录外 | 先弹一次确认框：`仅此一次` / `始终允许这个目录` / `取消`。选「始终允许」写进项目设置（`ProjectEntry.allowed_dirs`，**serde default**），以后新建的会话直接带上 |

关于第三点为什么不用网页的 `<input type=file>`：它只给文件内容、拿不到真实路径，而「原地引用」必须有路径。

项目外放行复用了既有的**额外根**机制（`extra_roots` → `pathutil::WriteRoots.extra`）：放行后读、写、列同步生效，提示词里的目录清单也会带上它。

## 6. 界面预览

| 类型 | 预览方式 |
|---|---|
| 表格 | 表格视图 + 行窗口化（只渲染可见行，手写、不引依赖）+ 工作表下拉 + 截断提示 |
| Word | 后端返回「`#` 标题 + `|` 表格」文本，前端按 markdown 渲染 |
| PDF | `pdfjs-dist` 在网页里渲染，逐页按需；后端取不到文字时提示「这是扫描件」 |
| 图片 / markdown / 代码 | 原有路径不变 |

表格数据与模型读到的是**同一条解析路径**：界面预览调用后端的 `read_for_preview`，它复用 `read_document` 的实现。两套解析逻辑迟早会对不上，所以不给预览单独写一条。

**预览通道的体积分档**（原先是所有文件一个 1MB 上限，那会把绝大多数表格和 PDF 挡在预览之外）：

| 通道 | 上限 | 说明 |
|---|---|---|
| 文本预览（`read_workspace_file`） | 8MB | 1MB → 8MB；再大就不该塞进网页视图 |
| 二进制预览（`read_workspace_file_base64`） | 8MB | 原为 1MB，会把 1MB 以上的图片也挡住（附件图片上限本身是 5MB） |
| 结构化文档预览（`preview_document`） | 200MB | 与 `read_document` 同口径 |
| 保真修改（`edit_document`） | 50MB | 改比读重（要解开 + 重打包） |
| 大文件取字节（`read_file_chunk`） | 200MB | 4MB 一片，供 PDF 阅读器按需取 |

200MB 这个值是**先按计划写死、待真实大文件验证**的，不是已经验证过的安全值。

PDF 阅读器的 `pdfjs-dist` 与 worker 都走动态 `import`（不打开 PDF 不加载那几百 KB），worker 脚本经 vite 打进产物、用同源相对路径引用，**运行时零下载**。CSP 相应放宽了三项：`script-src 'self' 'wasm-unsafe-eval'`、`worker-src 'self' blob:`。

## 7. 内置技能

新增三份内置技能 `xlsx` / `docx` / `pdf`，内容是「怎么做、哪些坑、失败案例索引」，不携带脚本。同时修正了 `doc-convert` 里两处过时说法（原先写「xlsx → csv 靠 python3+openpyxl」「pdf/docx 不在本 skill 范围，read 会拒绝二进制文档」）。

三份文案都是本项目自写的：参考市面上公开的 Office 文档处理经验与踩坑清单，但**没有携带第三方代码或原文**，也不需要随附许可证声明。

**一处刻意的取舍**：PDF 没有传 `wasmUrl`，所以 `cqms_bg.wasm` / `openjpeg.wasm`（ICC 色彩与 JPEG2000 的可选增强）不可用。不提供时 pdfjs 会打一条警告并回退（ICC 色彩空间降级、JPX 走 JS 回退），常规 PDF 不受影响。这样做是为了不给产物额外搬运两个二进制资源。

## 9. 已知限制（如实列出）

- **表格只取第一个窗口**：预览能看到 200 行 / 64 列（单次上限），有截断提示，但**没有翻页或按范围续取**的交互——大表在界面上只能看第一屏。
- **表格改公式后该单元格的缓存值被清掉**：Excel 打开时会自动重算，但不看公式的工具在那之前读到的是空值。这是有意的（要自己算就得实现一整个公式引擎），技能文档里写明了。
- **增删行列、增删段落表格不支持**：往表格中间插一行会连带影响合并区域、数据验证范围、图表引用与所有相对引用。
- **PDF 只渲染当前页**，无缩放、无文字选择。
- **中文 PDF 提取效果不保证**：文件如果没有内嵌字形对照表，提取结果会是乱码或缺失；此时如实告知使用者，不拿乱码当原文分析。
- **`.xlsm` 的宏不会被动到**，但也不提供编辑宏。
- **PDF「渲染失败」路径没有自动化测试**：happy-dom 下没有 canvas，自动化只能覆盖到「不进渲染器」的分支（扫描件提示）。
- **界面改动未做自动化点击验证**（项目约定：界面改动交付手动验证清单）。
