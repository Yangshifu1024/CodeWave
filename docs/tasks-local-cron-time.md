# 计划任务 cron 本地时间修复

日期：2026-09-26

## 现象与根因

计划任务列表同时显示“每天 09:00”和“下次触发 17:00”。前端将 `next_run` 中的 RFC3339 时区正确换算到本地；后端却以 `Schedule::upcoming(Utc)` 计算 cron，再转成本地。用户输入的 09:00 因而被当成 UTC 09:00，在 UTC+8 显示为 17:00，实际执行时刻也随之错了。

## 修复

- cron 根据传入的本地 `DateTime` 用 `Schedule::after(&now)` 求下一次触发；`every` 和 `once` 逻辑不变。
- 启动恢复任务时，检查已存储的 cron `next_run` 是否是最近一次本地触发；只重算不匹配的启用任务。原本匹配的过期时间仍留给既有 tick 逻辑处理，保留停机期间错过任务的处理方式。恢复后由现有 `upsert` 持久化修正结果。
- 用固定 UTC+8 时区测试“当天 08:30 → 当天 09:00”和“当天 09:30 → 次日 09:00”，并覆盖 `09:00,17:00` 两次触发时旧值 17:00 虽符合表达式、却不是最近一次触发的情况；另验证旧存储时间修复及匹配时间保留。
- 夏令时回拨时，cron 库可能先枚举已过去的第一次 01:30；下一次触发必须跳过不晚于 `now` 的候选。用纽约回拨日第二次 01:10 → 第二次 01:30 的测试守护。

`next_run` 是实际排程时间，因此单独改界面文案或显示换算不足以修复问题。

## 验证

`cargo fmt --check` 与完整 `cargo test --offline -- --test-threads=1` 通过：1258 passed、3 ignored。受限执行环境首次运行时，默认临时目录权限及进程树前提检查导致了环境相关失败；在正常 Windows 权限下完整重跑全绿。
