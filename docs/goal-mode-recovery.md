# 目标模式恢复与账本修订

> 2026-09-26 · 缺陷修复。现行目标模式的恢复与续跑语义以本文为准；初版设计见 [goal-mode](./goal-mode.md)。

## 故障与根因

用户的目标会话在 `~/.codewave/logs/codewave.log.2026-09-25` 中先后出现三条故障链：

1. 首次执行时，相对路径账本中的 `Cargo.toml` 等文件被判 `E_GOAL_OUTSIDE_LEDGER`，三次拒绝后暂停。这一条已由 `c9f31df` 将相对账本路径锚定会话 workspace 修复，本次保留对应回归测试。
2. 应用重启后，同一会话在 20:47 UTC 报 `E_PLAN_READONLY` / `E_TOOL_BLOCKED`：运行时的 `SessionPrefs` 只在内存中，重建时回落全局默认 Plan；前端也会用 `get_session_prefs` 的 Plan 覆盖已恢复的 Goal 胶囊。
3. 旧会话打开时 `load_session` 已填充 `rt.history`，而 `run_chat` 仅在历史为空时装载目标边车；于是右栏通过 `goal_view` 能看到目标，`goal` 工具却报 `E_GOAL_NOT_REGISTERED`。暂停目标边车内已有 8 次拒绝，`resume_goal` 原先不清计数，显式续跑也会再次立即停下。

另有实际合同遗漏 `ls` / `mkdir`：程序不在用户批准的白名单中，按账本拒绝是正确行为，不能静默扩权。过去没有在目标模式里修订已暂停合同的入口，用户无法顺畅恢复。

## 现行方案

- 目标档活动标记写入 `sessions/<id>.prefs.json`（原子写，随会话级联清理）；进入目标档、ask 切档、目标达成回落均同步落盘。旧会话无偏好边车而有未结束目标时恢复 Goal 档；已经落盘的显式非 Goal 档选择优先。重启发现 `executing` 目标时先持久化为 `paused`，由用户显式续跑。目标完成后的前档在重启时归一为全局默认；同一边车中的模型与思考力度恢复规则见 [session-model-recovery](./session-model-recovery.md)。
- runtime 创建时装载目标边车；`run_chat` 的目标装载兜底与历史是否为空解耦，保证打开旧会话后工具态与右栏一致。
- `ledger_denials` 是一次无人值守运行的拒绝窗口：达到 3 次仍硬停；用户点「继续推进」时清零窗口和停滞计数、消耗旧硬停标记，保留 `blocked` 记录与目标合同。账本仍不自动扩展，再次越界仍会被拦。
- 暂停态新增「修订目标」：显式退回只读澄清期，保留目标、标准与阻塞记录；用户发送修订要求后，模型可改账本/标准，须重新发起批准才能进入执行期。未再次批准前，文件写入与 shell 均不可用。

## 验证

- 后端回归：有历史的目标会话重建后保留 Goal 档、目标并重建安全的前档；旧目标无 prefs 边车可恢复；崩溃时的 executing 状态恢复为 paused；旧 FullAccess 不会在目标完成后跨重启复活；显式续跑重置拒绝窗口且保留阻塞历史；修订退回澄清期；prefs 边车读写、损坏降级与级联清理。
- 前端回归：暂停态「修订目标」调用 IPC 并显示澄清态；原续跑入口保持可用。
- 手动点验：打开旧暂停会话，胶囊应保持目标模式，右栏目标内容与状态一致；点「修订目标」后只读澄清，要求补入缺失程序并重新批准，应进入执行期正常运行。另一条路径是直接点「继续推进」：账本未变，已授权范围内的操作应能继续，越界仍会被拦。界面改动按项目约定由用户手动验证。
